# 世界书附加条目的版面（WB-2）

状态：2026-10-02 定版并发布（D45）；2026-10-03 用 Mac TT 自己的请求重新核对过一遍（第 2b 节）。英文版是正本 `worldbook-layout.md`；这一份是大白话的阅读版。
还没测的：新位置的规则在真模型上的标签率对照（第 6 节；手上有的现成数字在第 5b 节）。

## 1. 为什么要做

附加书一直只管内容，位置、深度、角色、排序从没对着卡自己的书、酒馆的全局世界书设置和提示缓存查过。这份记录真实的提示词顺序、每一类条目的决定、实测数字，
以及做包的人该怎么摆。

## 2. 真实的提示词顺序（一轮伊甸）

用酒馆自己的拼装抓的（测试酒馆 8010 端口，卡、卡的书、你的订阅版预设、附加书，全局世界书设置同 Mac TT：扫描深度 2、预算 100%、递归开、角色策略 1）。
下面的消息号来自一次 62 条消息的请求。

| 位置 | 落在这里的东西 |
|---|---|
| 消息 0-17 | 预设的各块 |
| 18 / 21 | 预设的 `<Lore>` 包裹开 / 关 |
| 19 | 「角色定义之前」的世界书：卡的常驻和关键词条目，按 order 从小到大。旧版面里我们的关键词条目（order 420-572）排在这条消息最后 |
| 20 | 「角色定义之后」：卡的两条（306、308），然后是我们的（901、902） |
| 聊天记录 | 卡的深度 4 系统条目（order 100）在倒数第六条消息前面 |
| 深度 2（系统） | 预设自己的文风块，旧版面里接着我们的规则（order 900） |
| 深度 0（用户） | 卡的变量更新规则和变量列表（order 200），新版面里接着我们的规则（order 900）——整条请求的最后一条消息 |

酒馆怎么排：条目按 order 从大到小处理，再插入，最终文字是从小到大（小的在前，大的最贴近聊天）。同深度同角色的深度条目合成一条消息；同一深度里系统消息排最后，
所以深度 0 时卡的用户块后面才是系统块。深度从末尾数：0 在最新一条消息之后，1 在它之前。

## 2b. 你自己 Mac TT 里的顺序（2026-10-03）

上面的表来自测试酒馆。你自己的 Mac TT 排法一样：这一行是从它的请求日志里读的（`llm-api-551.request.json`，152 条消息，模型 假流式-gemini-3.8-flash，

| 位置 | 落在这里的东西 |
|---|---|
| 152 条里的第 5 条（用户，59265 字符） | 卡的「角色定义之前」条目（order 100-400）和「之后」条目（306-309），接着是我们的两条常驻（901 事件类型、902 地点叫法）——合成一块，从小到大 |

这条实测值得记住的两点：我们的规则确实是模型最后读到的东西，紧跟在卡自己的末尾规则后面；Mac TT 把深度 1 和深度 0 的内容作为同一条末尾用户消息发出来
（关键词条目在前，深度 0 的按 order 在后）。这也说明为什么触发集合每轮变化不会挪动规则：两者都在整段历史之后。

## 3. 缓存需要什么（CCST，只读）

- Claude 的缓存按前缀匹配，只在末尾有一个消息级缓存点。请求前面任何一处变了，后面整段重写。
- CCST（默认「原位」）：第一条玩家消息之前的系统消息是被缓存的系统提示词；之后的系统消息变成用户文字并进玩家那一轮；比上一条回复更深的深度注入被挪到当前轮旁边。
- CCST 的 `lore_tail` 会学习哪个带标签的块总在变（这里是预设的 `<Lore>`）并把它搬进最新消息。它要第一次变化之后才生效、块要小于提示词的 60%、还得有包裹标签。
  原位模式下 `fold_tail` 用不上。
- 所以放在静态区（角色定义之前 / 之后）的关键词条目，一旦触发集合变了就整段历史重写，除非上面的学习恰好罩住它。放在最新消息上一条的关键词条目，只改请求的末尾。

## 4. 每一类条目的决定（D45）

| 类 | 灯 | 位置 | 深度 / 角色 | 排序 | 理由 |
|---|---|---|---|---|---|
| 说明 | 关（禁用） | 角色定义之前（从不注入） | - | 1 | 让装好的书自己说明自己；不占 token |
| 规则（`map.link-rules`） | 常驻（蓝） | 深度 | 0，用户 | 900 | 紧跟卡自己的回复末尾规则（它的深度 0 用户块，order 200），模型把两者读成同一块格式要求。最近几个伊甸聊天 17 层里只有 1 层带标签，那时我们的规则在卡的深度 0 规则上面的深度 2 系统块里 |
| 事件类型、地点叫法 | 常驻（蓝） | 角色定义之后 | - | 901、902 | 静态文字，每轮一样，留在被缓存的系统提示词里，每轮只花大约十分之一 |
| 关键词条目（129 条：方位、常识、地点、房间） | 关键词（绿） | 深度 | 1，系统 | 方位 910-929，常识 930-949，地点 950-999，房间 1000-1099 | 触发集合变了只改请求末尾；不靠代理学习、不靠包裹标签；资料贴着它回答的那句玩家话 |
| 聊天自定义书：索引 | 常驻 | 角色定义之后 | - | 903 | 静态 |
| 聊天自定义书：地点 | 关键词 | 深度 | 1，系统 | 1200+ | 同附加书的关键词条目 |

我们的 order 一律 900 起（说明条除外），不和卡的 100-500 交错。各段之间留了空号，以后加新的一族不用重排已装书的旧条目（order 改了，下次同步会跟着发布版面走）。
关键词条目的角色保持系统：测试里深度 1 用「用户」角色把缓存打坏了（第 5 节 BU 行）。
扫描深度保持全局值（2）：逐条加大只会让条目留得更久、多花 token，没有实测收益。
递归：我们的条目两个方向都禁止递归，不会触发卡的条目，也不会被卡的条目触发。预算：用全局（100%）。
JIT：开关条目会改变提示词（设置里的说明已写明），默认仍关。同步不会把 JIT 关掉的条目重新打开。

## 5. 实测

方法：用 CCST 代理的空跑模式（只准备请求并保存，不调模型），每种版面喂 12 个来自真实酒馆的请求：一份真实伊甸聊天的副本（19 条消息）加 12 个每轮换地点的脚本轮次
（最坏情形）。读缓存 = 与上一次请求相同的部分（先系统提示词，再历史，末尾一个缓存点）。单位是字符（这类文字约一字一 token）；「折算」按读 ×0.1、写 ×1.25。
共 11 次比较（第 2 到 12 轮）。N = 只有卡，没有附加书。

| 设置 | 版面 | 命中 | 每轮写入 | 每轮折算 |
|---|---|---|---|---|
| 原位，lore_tail 开（你的设置） | N | 93% | 10.3k | 27.1k |
| | A（WB-2 之前） | 93% | 10.4k | 27.9k |
| | B（已发布） | 93% | 10.3k | 27.7k |
| 原位，lore_tail 关 | N | 26% | 75.7k | 97.2k |
| | A | 0% | 104.0k | 130.0k |
| | B | 27% | 76.2k | 98.0k |
| 提到系统提示词（旧设置），lore_tail 开 | N | 94% | 7.0k | 19.3k |
| | A | 94% | 7.1k | 19.8k |
| | B | 77% | 26.5k | 42.0k |
| 原位，lore_tail 开 | BU（关键词条目用「用户」角色） | 19% | 67.2k | 85.7k |

读法：用你的 CCST，两种版面一样（代理把预设的 `<Lore>` 块搬走了）。没有这层（还没学到、换了别的代理、预设没有包裹标签、tail 关掉）时，A 每次触发集合一变就整段重写，
B 的开销和没装附加书一样。旧的「提到系统提示词」设置下 B 吃亏，因为系统消息被提进系统提示词：不是你的设置，接受。只把规则挪到深度 0 对缓存没有影响
（K1，规则在深度 2，测出和 B 一样）。局限：一个聊天、一个预设、一条脚本路线、空跑（没有轮次捕获）、`use_resume` 开；`use_resume` 关时 CCST 把整段历史折成一个字符串，不论什么版面都不缓存。

## 5b. 实际聊天里的标签率（不是对照实验）

| 时间窗 | 回复 | 带地图标签的 |
|---|---|---|
| 重写之前的整段聊天 | 73 | 6 |
| 紧邻重写的 7 条 | 7 | 5（各两条） |
| 重写之后的 11 条（版面 B） | 11 | 9（两到五条） |

读法是「没有变差」，不是「变好了」：2026-10-02 19:26 到重写之间那段时间书是缺的，所以前面两行混了「没有书」和旧的深度 2 规则；两个时间窗里你都没有催标签
（没有 `（OOC…）` 提醒，也没有粘贴标签）。版面 B 没有让模型不写标签；至于是不是写得更多，是第 6 节要定的。

## 6. 没测的

新版面 B 对旧版面 A 的标签率（Mac TT 里用 gg 配置、真模型）到现在也没做成对照：你的 Mac TT 一直在用（应用刚开没几分钟、聊天还在增长），
往你正在跑的角色扮演聊天里打字不合适。手上有的只是第 5b 节那组数字。要跑对照：用别的名字导入两本书，在新的伊甸聊天里一次绑一本（当全局书），
发 WB-1 的两句种子，各滑动 3 次，数存盘聊天文件里的 `⌖` 行。版面本身不用调模型就能查，用你机器上已经发出去的任意一条请求：
`python3 tools/wb_prompt_order.py <日志目录>/llm-api-NNN.request.json <book.json> <book.json> --all`。

## 7. 做包的人该怎么办

1. 每轮必须在、又不会变的常量：放角色定义之后，order 900 起。写短。
2. 模型回复末尾必须遵守的那一块规则：放深度 0，角色和卡自己的末尾规则一样，order 排在它们之上。
3. 靠词触发的一切：深度 1，系统角色。不要放角色定义之前或之后（会挪动被缓存的前缀）。每族条目给自己一段 order，段与段留空号（附加书用 910 / 930 / 950 / 1000，自定义书用 1200）。
4. 附加书用 900 以上的 order；卡自己用 100-500。不要动别的书的条目。
5. 每本生成的书第一条放一个禁用的说明条目（版本、写入时间、写入方、条数、怎么报 bug），地图脚本每次写书时重写它。
6. 每个发布的条目都带 `position`；版面改了，已装的书会跟着变，除非玩家手动挪过那一条。

## 8. 已装的书要不要删

不用。地图每次打开按条目编号原地更新这本书。WB-1 之前装的书保留条目：旧编号经别名表对到新编号，旧的「地图人物位置」条目作为没改过的重复丢掉（改过就留下并降到最低优先级），
条目重新启用（JIT 开着时它关掉的除外），WB-2 起它们的位置也跟着发布的版面走。改过名的旧书（手动导入、名字带版本号）会迁移到稳定书名和原来的绑定，旧书留着不动。
不会出现重复：条目按编号对应，不按名字。
