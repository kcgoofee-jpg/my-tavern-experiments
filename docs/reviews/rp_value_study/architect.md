# 架构师汇总：聊天 RP 场景下地图功能的价值（2026-09-27）

> 输入：六份人设报告 `p1_heavy_rp.md`（重度桌面 RP）、`p2_mobile_casual.md`（手机轻度）、`p3_card_author.md`（制卡作者）、`p4_lore_keeper.md`（设定党）、`p5_lowend_weaknet.md`（低端机 / 弱网）、`p6_fresh.md`（现编：B 站直播主播）。另读了 `ROADMAP.md`、`docs/GOAL_v0.9.1.md`、`tools/review/`（README、`pack.py` 的 `STAGES`、`personas/`、`architect_synthesis.md`）、`docs/ui-audit.md`、`docs/render-performance.md`、`docs/map-events.md`、`docs/event-taxonomy.md`、`docs/content-compat.md`、`map/tavern/eden-map.js`、`map/tavern/events.mjs`、`map/viewer.html`、`map/here.mjs` 和 git 历史。人设报告里提到的代码问题我逐条核对过（见 §5）。

## 结论先行

1. **用户的判断成立，而且数据比他说的还极端。** 六位人设给「全图美观」的平均分是 5.5，给「8K 深度细节」的只有 1.7；两项加起来只占注意力的 **9.5%**。「当前地点跟随 + 事件」占 **33.7%**，「稳定 + 秒开 + 手机」占 **31.7%**。唯一把美观打到 8 分的是直播主播，他要的也只是「一屏缩放下的整体观感」，不是 8K 细节。
2. **渲染已经过了「够用」线。** 真正烧时间的不是渲染本身，而是门控的设计：每一轮都有「写实 ≥ 7」「8K 局部」这两条近乎不会饱和的门槛，而且每轮的「遗留清单」会变成新的一条轨道（A3 → A6 → A7，B1 ×4 → B2 ×3，C3 做了 4 轮后冻结），「最多 3 轮」的上限因此一直在重新计数。按 git 记录估算，最近约 36 小时里 188 个提交中，约 84 个属于渲染 / 庄园轨，约 43 个属于查看器 / 事件 / UI；渲染类门控累计约 25 轮，墙钟时间约 15–20 小时，其中伊甸 three.js 精装这条线（约 6–8 小时）已经整体冻结，成了沉没成本。
3. **投入不足的地方正好是每天都会碰到的：** 事件窗口只有 40 楼，未解除的事件也会在 40 楼后消失；iOS 永远判不进省流；文档和代码不一致（楼数、关键词过滤）；慢网会自动进 3D 庄园；「地图 → 聊天」没有做；没有历史回看；地点出处只写「推断」两个字。
4. **新的渲染「够用」门槛：** 只严格审四件事——与设定一致、层 / 城区一眼可辨、标记可读、TT 内性能与内存。写实度和 8K 局部改成参考项，不再阻断门控。每个资产每个版本**最多 2 轮**，遗留问题进 backlog，不再开新轨道。
5. **v0.9.1 不延期**：上层 B2 以第 3 轮收尾，按最高分版本发；另外做 6 件小修（文档对齐、iOS 预加载、慢网不自动进 3D、事件窗口最小修、复测 R02、E6 收窄）。「地图 → 聊天」、时间线、Blender 庄园、通用化都不进 v0.9.1。

**产生过度投入的机制**（这比任何单次返修都重要）：
1. **门槛不饱和。** `pack.py` 的 `STAGES` 要求**每位**审阅 ≥ 7，其中「写实航拍」按「只看绝对水平」打分，永远能挑出下一处不像真实航拍的地方；`ROADMAP.md` 经验第 4 条又规定「每一轮都在 8K 局部精度下检查」。两者叠加，门槛实际上没有上限。
2. **遗留清单会变成新轨道。** A1 的遗留变成 A3，A3 的遗留变成 A6，A6 的遗留变成 A7，「最多 3 轮」每次都重新计数。每位审阅者按模板最多写 5 条问题，所以遗留清单永远不会是空的。
3. **没有一个审阅者代表「RP 玩家扫一眼」。** 现有的美术人设全是专业视角（遥感摄影师、程序化老手、园林史）。面板 UI 那组（`ui/rp`、`ui/phone`、`ui/weak_net`）才是 RP 视角，但它们不参与渲染门控。

## (b) 今后渲染的「够用」门槛

原则：**底图是 RP 的背景和定位参照，不是作品本身。** 门控只审 RP 用户在默认视野、标准档、375 px 手机 / 1080p 推流下看得到的东西。

### 保持严格（阻断门控）

| 维度 | 门槛 | 怎么审 |
|---|---|---|
| **与设定一致** | ≥ 7；地标位置与 `maps.json` 一致；跨层对应（检查点 ↔ 7 号井）不漂移；伊甸最大、最显眼；硬约束（机构只画中性外观） | `art/setting` + `check_maps.py`；**新增**：推断内容不能比设定内容画得更「确定」（P4），只写进意见、不加轮次 |
| **层 / 城区一眼可辨** | 在**省流档 2000 px 与 375 px 手机**上，10 秒内能说出「这是哪一层、哪片城区」；风格岛在默认视野下不像复制粘贴 | `art/readability` 改用省流档与手机截图作为主材料 |
| **标记可读** | 地标与事件标签不压在过曝块上，对比度 ≥ 4.5（深浅两种主题）；1080p 推流压缩后仍能读出（P6） | 查看器截图，不看裸底图 |
| **TT 内性能与内存** | 省流首屏 ≤ 3 s；单层标准档瓦片 ≤ 1.5 MB（中层 L12 实测 1.46 MB）；打开 / 关闭 20 次 JS 堆持平；流式输出不卡 | `tools/browser/accept.mjs` + 瓦片体积脚本 |
| **明显瑕疵**（二元判定，不打分） | 标准档（4000 px）默认视野里没有过曝白块、死黑区、UI 图标感的硬圈 / 描边、穿模、错位 | 这是 8K 局部唯一保留的用途：8K 只抽查锯齿 / 断线 / 怪影，结果只记「有 / 无」 |

### 放宽或取消

| 维度 | 处理 |
|---|---|
| 写实航拍（`art/realistic_aerial`） | **改为参考分，不阻断。** 参考门槛 ≥ 6；低于 6 且问题在标准档可见时，才算 P1 |
| 8K `--crop` 深度局部 | **取消打分。** 只保留上表中的二元瑕疵抽查；只在 8K 下可见的问题一律记为 P2 / backlog |
| 拼缝与重复感（`art/seams`） | 只在默认视野和标准档下判；「同风格 6 岛说得出区别」放宽为「默认视野下不像复制粘贴」 |
| 园林与建筑史（`art/garden_history`） | **改为参考**，不计入门控 |
| 写实度微调（车流密度、光池、色温、楼缝宽窄） | 不再单独开轮；只能搭在「设定一致」或「可辨」修复的同一轮里顺手做 |
| 伊甸庄园「每人 ≥ 8」「马桶 / 毛巾质感」 | 取消。庄园门槛 = 房间可辨 + 当前房间高亮正确 + 手机首帧 ≤ 2 s（4× 节流） |

### 轮次与发版规则
- **每个资产、每个版本最多 2 轮门控**。第 2 轮之后，不论分数多少，按**保留维度平均分最高**的版本发。
- **通过条件**：保留的四个维度（设定、可辨、标记、性能）每项 ≥ 7，且没有瑕疵 P0。写实度只作参考。
- **提前停止**：两轮之间保留维度平均分提升 < 0.5 时，不再做第 2 轮，直接发。
- **遗留不开新轨道**：遗留写进 `ROADMAP.md` 的 backlog。要重开渲染轮次，只能有两个理由：用户在 TT 实测截图里指出问题，或者设定变了。
- **8K 全图重渲**：每个版本每层最多一次，放在门控通过之后。
