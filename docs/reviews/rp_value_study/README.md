# 聊天 RP 场景下地图的价值研究（2026-09-27）

起因（用户原话）：「整个项目最耗时的渲染我们无法改变，但是实际体验上大家注重的可能不是渲染质量，毕竟以聊天 RP 为主」。

## 结论
**用户的判断成立。** 6 位人设都把「我在哪 + 出了什么事 + 快和稳」排在最前面，渲染画面两项（全图美观、8K 局部）加起来只占约 9.5% 的注意力。渲染已经够用。今后渲染门控只严格把关**与设定一致、一眼能认出层和区、标记可读、TT 内性能**这几项；写实度只作参考，8K 局部不再打分；每个资产每个版本最多 2 轮。省下的时间投到事件窗口、iOS 省流、地图 → 聊天、轻量呈现层（迷你条 / 低清 / 直播模式）、出处与推断的区分上。

## 渲染「够用」门槛（摘要，详见 architect.md (b)）
- **严格把关（不达标就不过门控）**：
  - 与设定一致 ≥ 7。
  - 在省流档 2000 px 和 375 px 手机屏上，一眼能认出是哪一层、哪片城区。
  - 标记可读：对比度 ≥ 4.5，1080p 推流后仍能读出。
  - TT 内性能：省流首屏 ≤ 3 s，单层标准档 ≤ 1.5 MB，开关面板 20 次后 JS 堆不增长。
  - 标准档下没有明显瑕疵（只判有或无，不打分）。
- **放宽**：写实度改为参考分（≥ 6，不阻断）；8K 局部只抽查瑕疵，不打分；园林史、拼缝两项改为参考。
- **轮次**：每个资产每个版本最多 2 轮；一轮提升不到 0.5 分就提前停；到上限按最高分的版本发；遗留问题进 backlog，不再开新轨道。
- **审阅人设**：新增 `art/rp_glance`（RP 玩家扫一眼），他可以否决「再开一轮」。

## 前 5 项投入（按价值 ÷ 工作量排）
1. **事件长期窗口**：未解除的事件不因楼层太旧而消失；加「我在这」按钮；标题栏的地点可以点。工作量 S。
2. **地图 → 聊天**：「去这里」「追问这件事」。工作量 M。
3. **轻量呈现层**：聊天内迷你条、纯文字 / 低清模式、直播模式开关。工作量 M。
4. **出处与推断**：出处带世界书条目号和推断依据；推断的地点在叠加层用虚线区分，不需要重渲。工作量 S–M。
5. **历史时间线 + NPC 公开行程**。工作量 M–L。

接入成本和配置校验属于通用化，等用户批准通用化后，排到第 2 项之前。
