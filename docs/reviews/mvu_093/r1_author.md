# r1 卡作者视角 — 7/10

1. P1｜wb「地图当前地点 v2」首段｜直接教模型「MVU『世界.当前地点』写到最具体的位置」并给格式（伊甸庄园·房间名 / 天城·层·地标），等于外挂规则改写了我 [mvu_update] 对自己字段的写法约定，也违反简报「不引用卡的字段名」。我改格式或改名后两套规则打架。｜改成只描述「地点叫法」（地图能识别哪些写法），不点名 MVU 字段、不说「写到」；或只在作者规则没有格式要求时作参考。
2. P1｜wb「地图人物位置 v1」末段「变量」｜「只有结构里本来就有『位置』时才一并改它」会诱导模型在 [mvu_update] 里尝试写 在场人物.X.位置（模型看不到 zod 结构，常会新增），被 zod 丢掉也浪费输出、可能触发 MVU 校验报错。｜删掉这句，位置只走 ⌖人物 标签；作者真加字段后由作者自己的规则负责。
3. P2｜EJS 方位条目｜getvar('stat_data.世界.当前地点',{defaults:''}) 在提示词模板里读的是合并后的消息变量，OK；[值,说明] 用 [].concat()[0] 已降级。但值若是对象会成 "[object Object]"（无害，无输出）；字段改名后静默无输出，自检没有提示。｜自检里加「当前地点字段未找到」提示；路径集中成常量便于我改名时对照。
4. P2｜eden-map.js writeVars｜updateVariablesWith 只动 eden_map 顶层键，正确；replaceVariables 分支是读-改-整表写，与 MVU/其他脚本并发时可能覆盖别人刚写的聊天变量。stat_data 在消息变量里不受影响。｜replaceVariables 分支排在 insertOrAssign 之后，或写前重读并只替换 eden_map。
5. P2｜docs/author-compat.md｜语气客气、可选、说清原因，合适。缺两点：地图还依赖 世界.当前地点 / 世界时间 / 主角.着装 的路径（改名会让方位与夜色失效），以及附加条目的列表，便于作者判断冲突。｜加一节「地图只读的路径」与「附加条目清单」。

兼容性：在场人物对象/数组/字符串均已处理（mvu.mjs PRESENT_KEYS + 多形态），加字段无影响；从不写 stat_data 已确认。

结论：数据隔离做得干净，主要问题是两条附加条目越界指导模型写作者的 MVU 字段，删掉那两处即可放心。
