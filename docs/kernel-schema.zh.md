## 1. 原则

### 1.1 内核定形状，包给内容

**K-R01 —— 内核定形状，包给内容。** 内核负责：消息协议、每种实体的核心字段、算法（定位、合并、老化、多来源优先级）、
渲染积木、安全规则。包只提供内容。包是纯数据：引擎从不执行包里的任何东西——不收脚本、不收表达式、不收正则——也从不把包里的
文字交给宿主里会执行它的功能（宏、模板、正则关键词：K-R65）。包里的词按字面匹配：整词或子串（K-R15；v1 的正则表改成词表）。
包能做什么，还取决于它是从哪来的（K-R63）。

**K-R02 —— 永久固定 vs 作者可定义。** 改左列任何一项都要升 schema 版本号（K-R62）。

| 方面 | 内核固定 | 作者可定义（包数据） |
|---|---|---|
| 空间 | 节点核心字段与 id 规则；定位算法（K-R17–K-R23）；视图种类与坐标系；落点规则 | 任意深度的节点、作者自己起名的类型；别名、弱词、坐标、视图、层切换条 |
| 时间 | 确定性时钟推进（零 token）；HH:MM 解析；时段规则 | MVU 路径；时段（名字、起点、对应词、是否夜景） |
| 人物 | 核心字段 `id`、`name`、`node`、`source`；来源优先级；四种字段展示方式 | 分组（名字 + 来源）、属性字段、头像来源与允许的域名 |
| 物品 | 藏物行结构；仓库键规则；账本对账；「聊天记录是唯一真相」；拾取的严格度（动词 + 具体名词） | 世界藏物；拾取词表的增补与停用 |
| 事件 | 标签语法；等级数字 0–3；合并与老化算法；从不过滤内容；认不出的类型 → `other` | 大类、类型（名字、别名、图标、颜色、特效预设、寿命、是否注入）、等级名、结束词、示例 |
| 图层 | 10 个槽位及其顺序；渲染积木 | 声明式图层（S8） |
| 界面 | 设计令牌体系；z-index 阶梯；无障碍底线；标签页集合 | 文案、强调色与令牌覆盖、图例、标签页顺序、起始节点 |
| 与模型的接口 | 注入预算与降级顺序；同意开关；只写我们自己的附加世界书 | 各语言的注入模板、世界书规则条目、书名 |
| 宿主 | MVU / 酒馆助手适配器；存储命名空间规则；CDN 线路；消息协议；按来源分信任（K-R63） | 旧名字与 CDN 线路（只限随引擎发布的包） |
| 三维 | 通用查看器及其清单格式 | 模型、热点（视图的区域） |

### 1.2 数据规则

**K-R03 —— 有顺序的用数组，只查找的用对象。** 顺序有意义的一律是带 `id` 的对象数组：节点、事件大类、人物分组与字段、
时段、图层。只按 id 查的一律是以 id 为键的对象：视图、事件类型、特效预设、按语言分的表。数组顺序在哪里起作用，相应规则里写明。

**K-R04 —— 键与标识。** 键一律 ASCII `snake_case`；id 一律 ASCII（`^[a-z][a-z0-9_]*$` 一类）。显示文字放在值里，
任何语言都行；卡原名照抄进值。以 `_` 开头的键是注释；以 `x-` 开头的键是作者扩展：原样携带，内核从不读（以后的 schema
可能把某个 `x-` 升格为正式字段）。这两种键允许出现在：清单顶层、每个块的顶层、以及列表或「按 id 为键的表」里的每一项（节点、
通道、视图、分组、类型、字段、时段、藏物行、世界书条目、头像块）；其余对象一律封闭。

## 2. 包的布局与清单

### 2.1 一个文档，各块内联或拆成文件

- 一个包就是一个 JSON 文档 `manifest.json`。九个块（`nodes`、`views`、`vars`、`entities`、`items`、`events`、
  `layers`、`ui`、`llm`）各自可以直接写在清单里，也可以写一个相对路径，指向只装这一个块的 `.json` 文件。两种写法用同一份 schema。
- 内嵌在角色卡里的包（S9）就是「全部内联」的写法；仓库里的包通常把大块拆成文件。
- 路径相对清单所在目录（第一个包例外：相对 `map/`，直到 S10 把它的数据搬家）。只许 `^[A-Za-z0-9_][A-Za-z0-9_./-]*$`，
  且不含 `..` 段：不收协议头、不收 `/` 开头、不收 `%`、不收反斜杠。按网址解析之后还必须落在包的根目录下，否则丢掉（K-R64）。
  内嵌在卡里的包没有目录；它能不能带图见 K-09。

### 2.2 清单字段

| 字段 | 必填 | 含义 | 缺省 |
|---|---|---|---|
| `id` | 是 | `^[a-z][a-z0-9_-]{1,31}$`，等于目录名 | — |
| `schema` | 是 | `2` | — |
| `title` | 是 | 面板标题，1–80 字 | — |
| `lang` | 否 | 包里自己那些词的语言（K-R07） | 界面语言 |
| `version` | 否 | 包自己的版本标签 | 无 |
| `i18n` | 否 | `{ <语言>: { title } }` | 无 |
| `match` | 否 | 给 S9 预留（§2.3） | 不自动选中 |
| `credits` | 否 | `card`、`pack[]`、`assets[]`（K-R08） | 卡的字段运行时读取 |
| `legacy` | 否 | v2 之前用过的名字（§11，K-R09）；只限随引擎发布的包（K-R63） | 由 `id` 推出（K-R05） |
| `features` | 否 | 功能开关覆盖；外来包只能用它关功能（K-R63） | 按有哪些块推出 |
| `cdn` | 否 | `repo` / `npm` 资源线路；只限随引擎发布的包（K-R63） | 引擎线路 |
| `lexicon` | 否 | 按语言给内核词表的增补（K-R07） | 无 |
| 九个块 | 否 | 内联或路径 | 见 §12 |

**K-R05 —— 由 id 推出的名字。** 聊天变量 `spatial_<id>`（连字符换成下划线）、本机存储前缀 `spatial.<id>.`、协议前缀 `spatial:`、
事件属性 `data-spatial-event`。世界书：我们的条目带 `extra.spatial_id = "<包 id>/<条目 id>"`（外加 `spatial_ver`、`spatial_hash`）；
同步只动 `spatial_id` 以自己包 id 开头的条目。附加书的书名 = `llm.worldbook.book`（缺省用标题）再接一个固定的内核后缀，所以它
永远不会是卡自带的那本书（宿主按卡名给卡的书命名）；内核只写以这个后缀结尾的书。包的 `legacy` 块决定还要读哪些旧名（§11）。K-05 待定。

**K-R06 —— 工具严格，运行时宽松。** 工具对任何 schema、树结构或引用错误都报错：`tools/check_pack.py` 查它列出的那些，
`map/core/pack-v2.mjs validate2` 全查（S1-impl-1）。运行时逐项自愈，能少丢就少丢：
1. 凡是该写 id 的地方（节点 id 和每一处对它的引用）先修 id：转小写，`[a-z0-9_]` 以外的字符换成 `_`，修完不是字母开头就加 `n_`。
2. 修完仍然不合法的那一项丢掉；类型不对的字段丢掉；不认识的键忽略。
3. 只有块本身的顶层类型不对时，才把整块换成缺省（§12）。
每一次修补和丢弃都是自检列表（设置页）里的一条，从不弹窗：面板从不卡住，也从不要求用户去修包（简报规则 6）。查看器里的导出一律先过
`validate2`，只写出合法的包。

**K-R07 —— 语言。** `lang` 决定内核词表：途中句式、词尾后缀、句首冠词、中心词位置（K-R21）、结束词、拾取动词、按字段名自动发现用的词、
默认事件分类的名字、注入模板。内核自带 `zh` 和 `en`；其他语言用 `en` 的内核词表。包可以在 `lexicon.<语言>` 里按语言增补字面词：
`to` 与 `from`（途中标记，K-R19）、`articles`（冠词）、`suffixes`（词尾）、`fields.<变量>`（自动发现用的字段名，K-R38）、
`present`（表示「和玩家在一起」的词，K-R41）、`head`（`first` | `last`）。增补只加不减。匹配规则本身对所有语言相同（K-R15、K-R17）。

**K-R08 —— 署名只放一处。** `credits` 属于清单（它原本在 `ui` 里也出现过；合并成一处，因为选包时界面还不存在就要用到它）。
`credits.card` 可以在运行时由「版权申明」页用的同一座读卡桥填上（卡名、作者、版本）；包里写了的以包为准。

### 2.3 给 S9 预留：按卡匹配与内嵌

**K-R90 —— 包的解析。** 启动时和每次换卡时，宿主为当前卡解析出一个包；第一个给出可用包的来源胜出：（0）用户为这张卡的选择，或烘进脚本的包；
（1）卡内嵌的包（K-R91）；（2）索引里得分最高的匹配（K-R92）；（3）自动包（在它落地前是一个只有根的 schema-2 包，以卡名命名，
id = `c_` + `fnv36(卡名 + "\n" + 头像)`；完全读不到卡、或读不到索引时，用旧默认包）。被拒绝的来源（`validate2` 不给包、取不到、超上限）
落到下一档，并在 `window.__packProblems` 留一条；不挡、不弹窗。结果是 `{ id, source: choice | baked | card | index | auto,
trust: shipped | foreign, schema, manifest }`；只有随地图发布的索引里的包才是 `shipped`（K-R63）。结果是 id 等于 `core/pack.mjs`
`DEFAULT_ID` 的内置包（拥有旧名字的那个）时，不设 `window.__tcPack`，宿主与 S9 之前完全一样地启动（所有名字、键、注入文字不变）。
用户的选择按卡键存（`k` + `fnv36(卡名 + "\n" + 头像)`，读不到卡为 `k0`），键名 `edenMapPackPick`。门卫 300 ms 内解析完；超时先按旧默认包
启动，再用重启纠正。换卡时重新解析，包 id 或来源变了就停掉运行中的实例、重新求值入口。解析只读卡、卡自己的世界书、聊天变量的顶层键、内置索引
和用户的选择；什么也不上传。

**K-R91 —— 卡内嵌的包。** 按顺序读：（1）卡的 `data.extensions.spatial_os`——一个对象（整份清单，所有块内联）或一段 JSON 字符串；
（2）卡自己的世界书（当前角色的主书与附加书；绝不读全局书或聊天书）里按书序、条目序第一条标题（`name`，旧宿主 `comment`）去掉首尾空白后等于
`spatial_os:pack` 的条目，正文是 JSON 文本。条目启用与否都读（作者应当禁用它，宿主就不会把它发给模型）。包必须是 schema 2、块全内联、
至多 1 MB，并按外来包过 `validate2`；id 与内置包重名的拒收（K-R63）。引擎从不写卡或它的书。

**K-R92 —— 内置索引。** `map/packs/index.json` = `{ "schema": 1, "default": "<包 id>", "packs": [ { "id", "schema", "title", "i18n"?,
"match"? } ] }`，每个内置包一行，按显示顺序；`match` 与清单同形（`card.name | creator | tags`、`worldbook`）。schema-2 包的行里 `match` 等于
它清单里的；schema-1 包的 `match` 只在这一行里（`tools/check_pack.py` 检查索引）。一个包对当前卡的得分：聊天变量里有它的聊天变量作顶层键且值是对象 100；
`match.card.name` 的某个词出现在卡名里（规范化 K-R17，子串）10；`match.card.creator` 的某个词出现在作者里 10；`match.card.tags` 的某个词等于卡的某个标签 10；
`match.worldbook` 里每个标题与卡自己世界书的某个条目标题相等（规范化）5。得分 ≥ 10 才是候选；分高者胜，同分按索引顺序。*I-26：* 三类 `match.card` 的词只在包没有列出 `match.worldbook` 标题、或至少有一个标题命中（或聊天变量在）时才计分；同一作者所有卡共有的作者词不能单独打开一个包。词是字面字符串（K-R01）。
`default` 只由单独打开的查看器读。

**K-R99 —— 导入包。** 用户在设置里给一个 https 网址或选一个文件（消息 `eden-map:pack-pick`）。网址不带凭据、不带 referrer 地取，流式读取，上限 8 MB，
按 JSON 解析；文件同样读。只收 schema 2；写成路径的块，网址包按网址所在文件夹解析（必须留在它下面，K-R64），文件包则拒收。包按外来包过
`validate2`，所以它自己的上限（K-R66）照样适用。文件包的文本与网址包最后一份好副本按卡键存在本机（IndexedDB `edenMapPacks`）；每次启动重新取网址，
取不到就用副本。被拒绝的导入只在「地图包」框里显示一行被动提示，原来的包照旧。

### 2.4 信任与上限

**K-R63 —— 按来源分信任。** 来自引擎自己仓库索引的包（以及这种包经 compat-v1 转出来的结果）是「随引擎发布的包」；其余的包——内嵌在
卡里的、从网址或文件加载的、零配置长出来再导出的——都是「外来包」。由加载器按「从哪拿到的」来判定，从不看包里的字段；compat 的输出
沿用输入的等级。外来包：
- 忽略 `cdn`、`legacy`、`x-page`；引擎自己的代码永远从脚本自己的网址加载，包的线路只用来取包自己的资源文件；
- `features` 只能用来关功能；
- id 和某个随引擎发布的包相同 → 拒绝加载；
- 要过 K-R66 的上限和 K-R65 的模型文字规则。

**K-R64 —— 包里的值一律当不可信文本。** 包里的字符串只以纯文本进页面（`textContent` 或内核的转义函数），从不当标记解析。凡是要进
样式、网址、class 或其他属性的包里的值（颜色、图标、主题令牌、路径、头像域名），运行时再按 schema 里完全相同的正则查一遍，不合格就丢；
路径按网址解析后必须仍在包的根目录下。随引擎发布的包也一样。通用三维查看器的清单同样是包数据、同样受这条约束（S8 给它写 v2 schema）。

**K-R66 —— 外来包的上限。** 在 K-R27 之外，外来包还要裁到下面的上限（超出的项按 K-R06 丢掉）：

| 项目 | 上限 |
|---|---|
| 解析完块文件后的整个文档 | 内嵌在角色卡里 1 MB；从网址或文件读取、或由导出写出时 8 MB（Z-12） |
| JSON 嵌套深度 | 16 |
| 任何数组（规则另有写明的除外） | 1000 项 |
| 任何字符串（`desc`、世界书 `content` 见 K-R65） | 4000 字 |
| 词表里不同的词 | 20 000 个 |
| 共用同一个词的节点 | 8 个 |
| `x-` 键 | 保留，计入大小上限 |
| `media` | 至多 200 项；`media.*.src` 里的 data URL 不受字符串上限限制、但计入文档大小；单张图解码后至多 3 MB（K-R101） |

`validate2` 按来源取文档上限：`source: 'card'` 为 1 MB，`'url'`、`'file'`、`'export'` 为 8 MB，显式的 `maxBytes` 优先；两者都没给时是 1 MB。加载方传入自己读取的来源（`importPack`：请求的种类；查看器：内嵌在卡里的包是 `card`，其余是 `file`）。

**K-R98 —— 导出为包。** 对外来包（自动包、内嵌包、导入包或网址包），「导出为设定包」（设置 → 高级 → 地图包）写出一个 JSON 文件 `<包 id>.pack.json`
（`core/pack-export.mjs`）：当前的包，所有块内联，再加上长出来的节点（当作普通节点，`g_` id 保留，K-R10）、用户给地点起的叫法（作为对应节点的叫法，Z-16；
节点不存在的叫法丢掉），以及按卡信息填好的 `credits.card`（K-R08）。文件里没有聊天状态（藏物、迷雾、事件、忽略名单、账本、`chat`）、没有隐式视图，
也没有内核只对随引擎发布的包才读的字段（`cdn`、`legacy`、`x-page`）。id 保留（Z-06）。键按固定顺序写出，所以把导入的文件再导出一次，字节完全相同。
文件必须按外来包过 `validate2` 且没有任何问题，并且不超过 8 MB（`validate2` 用 `maxBytes` 取这个上限）；否则导出列出问题、什么也不写。紧凑形式小于 1 MB 的
标「放得进角色卡」。第二个按钮复制紧凑文本，用来新建标题为 `spatial_os:pack` 的世界书条目（包设置里提示：这个条目要保持停用）。编辑草稿（K-R100）并入（`exportPack(pack, { draft })`），包图片（K-R101）作为 data URL 内联随包走；私有图片永远不走（K-R102）。**叠加层导出（Z-15）：** 随引擎发布的包把草稿写成 `<包 id>.overlay.json`，形状同 K-R67（`schema`、带 `id` 与改动过的 `at`、`parent`、`alias`、`media` 的 `nodes`，新地点带名字，`media`，`ui.start`；没有 views）：只含改动，交给维护者合并进 `map/packs/<id>/overlay.v2.json`，旧的图集维护者流程由此取消。

**K-R101 —— 包图片。** 可选的第十个块 `media`（在 schema 2 内新增，K-R62；`map/data/schema/v2/media.schema.json`）= `{ <media id>: { src, w?, h?, note?, i18n?: { <语言>: { note } }, credit? } }`（id 为 `^[a-z][a-z0-9_]{0,63}$`，至多 200 项），外加节点字段 `media: [<media id>]`（这个节点的图集，按顺序，至多 32 张；块里没有的 id 记为 `ref-media` 并丢掉）和 `image` 视图字段 `media`（`src` 的替代：image 视图二者必有其一）。`src` 只有三种（`core/pack-media.mjs`）：
1. 包根目录下、以 `.webp`、`.png`、`.jpg` 或 `.jpeg` 结尾的相对路径（随引擎发布的包与网址包；不能有 `..`、协议、反斜杠；按网址解析后必须仍在根目录下；卡内包与文件包没有根目录，路径一律拒绝）；
2. `data:image/(webp|png|jpeg);base64,` 加 base64 文本，解码后至多 3 MB（任何包）；
3. 带图片文件类型、没有查询串和片段的 `https://` 地址，只在查看器开关「加载设定包里用链接给出的图片」（`edenMapPackRemote`，默认关，Z-13）打开时才加载；关着时这一项留作占位，只显示它的说明文字。
其他一切（`javascript:`、`http:`、`data:text/html`、`data:image/svg+xml`、查询串、超过 3 MB）都拒绝：这一项连同一条问题（`pattern` 或 `limit-media`）被丢掉，永远到不了页面。页面运行时再按同样的正则查每个值（K-R64）：`checkMedia`、`mediaUrl`、`nodePictures`。说明与署名一律作文字显示。画面是包图片的 image 视图由查看器经 `mediaUrl` 打开（被拒绝时记 `view-media`）。

**K-R102 —— 私有图片。** 用户可以给任何地点加只给自己看的图片。它们只在这个浏览器里（图集 IndexedDB，记录按作用域、`n:<节点 id>` 与图片 id 存放；作用域「本聊天」「全部聊天」同以前），**永远**不会被导出、内嵌、发给宿主或放进网址：没有任何导出函数读它们（`exportPack` 只读它文档写明的选项）。地点的图集先显示包图片、再显示私有图片；S9b 之前按房间名存的记录通过节点的名字找到（Z-18）；存着的可见性 `public` 读作 `private`。编辑模式下可以把一张私有图片复制进包（「加入设定包」），这会在草稿里新建一张包图片；私有记录仍然是私有的。

### 3.2 id

**K-R10 —— 节点 id。** `^[a-z][a-z0-9_]{0,63}$`，包内唯一，永久不变：聊天变量、藏物、迷雾、玩家起的叫法、协议消息都按它引用。
删掉的节点，它的 id 不再给别的地方用。自动生长（K-R26）产生 `g_` 开头的 id；导出的包保留它们，作者不手写新的 `g_` id。
`__root` 是内核补出来的根的 id：只存在于运行时，从不出现在包数据里（不写 `parent`、不写 `ui.start` 本来就表示「根」）。

**K-R11 —— 名字；不设出处标签。** `name` 必填。契约在节点上不设「卡里写明 / 自设」这类出处字段（用户决定 2026-09-30）；
`cite` 只是可选的自由文字来源备注，内核从不解读。自动长出来的节点只靠 `g_` 前缀识别。

### 3.3 树

**K-R12 —— 只有一个根。** 根的候选 = 没有 `parent` 键的节点。恰好一个时它就是根；一个都没有或有好几个时，内核补一个 `__root`
（名字用包标题），把所有候选挂到它下面。然后按声明顺序：`parent` 指向不存在的节点 → 挂到根下（它不算候选）；发现某个节点是它自己的祖先
→ 把它挂回根，环就在这里断开。好几个根是合法的；`parent` 不存在和成环，工具报错，运行时自愈，各记一条自检。

**K-R13 —— 顺序。** 声明顺序就是兄弟之间的顺序（层切换条、示意图布局、列表），也是定位的最后一道平局规则：靠前的赢。

**K-R14 —— 类型随意起。** `type` 是开放词表，用于图例、示意图和 `ui.legend`。内核从不按类型的值走不同分支。

### 3.4 词表：强叫法与弱词

**K-R15 —— 强叫法（alias）与匹配。** 写了 `alias` 就是完整的强叫法表；它必须包含 `name`，除非 `name` 放在 `hints` 里（工具检查；
运行时不自动补）。没写时，强叫法 = `name` 加上各语言的 `i18n.<语言>.name`，各自去掉包语言的句首冠词（`The Salty Dog` → `Salty Dog`）。
同一个强叫法出现在两个互不为祖先的节点上，就是有歧义的词，在两边都按弱词算。匹配比较的是预处理后的形式（K-R17）：
- 词的第一个字符是「用空格分词的文字」（拉丁、希腊、西里尔字母）或数字时，文字里它前面的那个字符不能也是这类字符；
- 词尾同理，但允许紧跟一个该语言的词尾后缀（英文：`'s`、`s'`、`es`、`s`），后缀之后再要求边界；
- 词的开头或结尾是其他文字（汉字、假名、韩文等）时，那一端按普通子串匹配。

所以 `pier` 能匹配「piers」「the pier's」，匹配不到「pierced」；`灯笼码头` 在任何中文句子里都能匹配。空串忽略。

**K-R16 —— 弱词（hints）。** 节点 N 的弱词意思是「在 N 里面的某处」。它最多只能落到 N，不会落到 N 的下级；遇到 N 这片以外的强叫法就让位（K-R22）。
同一个节点上，一个词既在强叫法里又在弱词里，按弱词算。根的弱词标记有歧义的词（「某处，不确定」）：它会盖掉藏在它里面的更短的命中
（K-R20），然后被移除，所以它自己从不决定结果。这一个概念取代了 v1 的三套机制：事件分层正则、「房间名要有上下文才算」规则、全局「泛称」表。

### 3.5 定位算法

输入：一段地点文字，可选再给一个节点 id `here`（K-R24）；输出：结果（K-R23）或 `null`。所有使用方共用这一套（K-R24）。

**K-R17 —— 预处理。** 对文字和词表里的每个词都做：Unicode NFKC；转小写；弯引号、撇号统一成 `'` 或 `"`；各种破折号统一成 `-`；
各种空白统一成空格；`&` 换成 ` and `；连续空格并成一个；去首尾空白。文字还要去掉宿主宏 `{{user}}`。长度（`len`）按预处理后的
字符数算。文字空了就 `null`。

**K-R18 —— 写了多处。** 按 `/`、`|` 拆开（NFKC 之后全角的 `／`、`｜` 也在内），依次定位，第一个认出来的为准；全都认不出 → `null`。

**K-R19 —— 在路上。** 按下面的顺序试这些句式；句式前面的文字接到 A 前面（和 v1 一样）：
- 中文：v1 `here.mjs parseTransit` 的句式原样照搬（从A到B 及其各种动词、A至B、前往 / 去往 / … B，以及它的尾词）；
- 所有语言：`^(.+?)\s*(?:→|->|⇒)\s*(.+)$` → A、B；
- 英文，不分大小写：`^(.*?)\bfrom\s+(.+?)\s+to\s+(.+)$` → 前缀、A、B；以及
  `^(.*?)\b(?:on (?:the|my|our|his|her|their) way|heading|headed|en route|bound)\s+(?:to|for)\s+(.+)$` → A、B；
- 包的 `lexicon.<语言>.from` / `.to` 标记，按整词匹配：`<from> A <to> B` 或 `A <to> B`。

结果 = A 的落点，A 认不出就用 B 的，外加 `transit: { from, to, from_text, to_text, route }`，其中 `from`、`to` 是节点 id 或 `null`，
`route` 是 v1 的「途经」文字。B 认不出、而 A 以「某某·」或「某某・」开头时，用这个前缀 + B 再试一次；只有落到比前缀本身更深的地方才算数
（前缀本身认不出时，认出什么都算）。两端都认不出时，把整段文字当作不是「在路上」来定位。

**K-R20 —— 命中与重叠规则。** 把词表里每个词（强叫法、弱词、玩家叫法）在文字里的每一处出现都记下来：
`{ node, word, weak, start, end, len }`。如果某处命中完全落在另一处更长命中的范围里，就丢掉它——不管两者属于哪个节点；
范围完全相同的命中都保留。然后移除根的弱词（K-R16）。最多保留 256 处命中，靠前的优先。

**K-R21 —— 强叫法一轮。** 候选 = 至少有一处留下来的强命中的节点；`best(n)` = n 最长的那处强命中（一样长取靠前的）。
`score(c)` = c 本身以及 c 的每个「也有强命中的祖先」的 `len(best)` 之和——也就是这个答案能解释掉多少文字。
胜者 A：分数最高 → 更深 → 自己的 `best` 更长 → 中心词位置 → 声明更靠前。中心词位置：中心词在前的语言（`first`：英文和其他
用空格分词的语言）`best` 靠前的赢（「market square by Lantern Docks」→ 市场）；中心词在后的语言（`last`：中文、日文，「B旁的A」）
靠后的赢。

**K-R22 —— 弱词一轮。** 弱命中的排序：词更长 → （给了 `here` 时）在树上离 `here` 更近 → 节点更深 → 中心词位置 → 声明靠前 →
在该节点 `hints` 里靠前。
1. 有 A：A 的「严格下级」节点上排第一的弱命中就是结果（弱词只能把 A 往下细化）；没有，结果就是 A。
2. 没有 A：全部弱命中里排第一的就是结果。
3. 一处都没留下 → `null`。

**K-R23 —— 结果。** `{ node, word, via, canonical?, transit?, text }`。`via` 说明 `node` 是哪一轮给出的：强叫法一轮给出的是
`alias`（A 自己的弱词只提供 `word` 时也算这一轮），K-R22 第 1–2 步给出的是 `hint`，起决定作用的是玩家叫法时为 `user`。
`word` = `node` 最细的证据：它自己有留下来的弱命中就取最好的那个，否则取 `best(node)`。`canonical` = 玩家叫法所代表的原词。
`text` = 预处理后的输入。

```
locate(文字, here?):
  t = 预处理(文字);              空 → null                                  # K-R17
  若写了多处 → 依次 locate(每处, here)，取第一个非空                           # K-R18
  若是「在路上」：r = resolve(A) ?? resolve(B)（+ 前缀重试）                   # K-R19
                 r 非空 → r 附带途中信息
  return resolve(t)
resolve(t):
  M = 所有命中，去掉被更长命中盖住的，再去掉根的弱词                           # K-R20
  A = 有强命中的节点里按（分数, 深度, best 长度, 中心词, -声明序）取最好        # K-R21
  弱命中按（长度, -离 here 的距离, 深度, 中心词, -声明序, -词序）排序           # K-R22
  有 A：h = A 严格下级上排第一的弱命中 → h ?? A
  没 A：h = 排第一的弱命中 → h ?? null
```

### 3.6 平局规则与「认不出」的情形

| 情形 | 结果 | 规则 |
|---|---|---|
| 同一条链上的两个名字（「城 · 区」） | 更深的那个（它的分数包含了祖先的） | K-R21 |
| 一个短名字藏在别处的长名字里 | 只算长名字 | K-R20 |
| 两个分支上的名字，长短不同 | 能解释更多文字的那一支 | K-R21 |
| 分数相同、深度相同 | 自己的词更长的，再比中心词位置，再比声明靠前 | K-R21 |
| 通用房间名 + 写了房子本身或它的某个上级 | 那间房 | K-R22 |
| 通用房间名 + 写了一个不相干的地方 | 那个不相干的地方 | K-R22 |
| 只写了通用房间名 | 那间房 | K-R22 |
| 两栋房子里都有的通用词，给了 `here` | 离 `here` 更近的那个 | K-R22 |
| 只写了一个泛称（根的弱词） | `null`；它还会盖掉藏在它里面的短名字 | K-R16、K-R20 |
| 泛称 + 另一个弱词 | 那个弱词 | K-R16、K-R22 |
| 一个强叫法挂在两个分支上 | 两边都按弱词算 | K-R15 |
| 两个节点的弱词、没有强叫法 | 最长的弱词，再比更近、更深、中心词、靠前 | K-R22 |
| 一个词藏在更长的英文单词里（「pierced」里的 pier） | 不算命中 | K-R15 |
| 写了多处「A / B」 | 第一个认得出的 | K-R18 |
| 在路上 | 起点，起点认不出用终点，附带途中信息 | K-R19 |
| 只有认不出的词 | `null` → 「未上图」（K-R25） | K-R22 |

### 3.7 事件、人物、物品也用同一套落点

**K-R24 —— 一套落点规则。** 凡是写了地点的——当前地点、事件的地点和范围、人物的位置、行程两端、用文字写位置的藏物——
一律按 K-R17–K-R23 定位：先强叫法，再弱词，最后「认不出」。`here` 的取法：定位当前地点时是上一次的当前地点；事件、人物、行程的地点
用玩家当前所在的节点；藏物不给。这些都能从聊天记录重算出来，所以结果仍然是确定的（简报规则 4）。认不出（`null`）怎么处理由使用方
各自规定：当前地点保持不动；事件按 K-01；人物进「位置不详」组；行程那一端丢掉。

### 3.8 玩家叫法、忽略名单、未上图

**K-R25 —— 玩家自己的词。** 玩家叫法是 `{ word, node, canonical? }`，存在包的聊天变量里（v1 的「自定义」；键名 S10 定）。
它的强弱跟着 `canonical` 在那个节点上的强弱走（是弱词就算弱），没有 `canonical` 就算强。节点或原词不存在的叫法忽略。
忽略名单 = 玩家选了「忽略」的名字。`unmapped(文字)`（即 v1 的 `unmappedName`）：预处理后为空、定位得到（在路上时任一端定位得到就算）、
或者忽略名单里有整段文字或它的第一处（K-R18）时，返回 `null`；否则返回第一处（给「未上图」小窗用）。

### 3.9 零配置：没有 nodes 块时从聊天里长出来

**K-R26 —— 从聊天里长节点。** 没有 `nodes` 块（或是空的）时，根是 `__root`，名字用包标题（S9 之后用卡名）。这条规则由 S9 对自动包实现（K-R95）：它在造出来的节点之上运行，根是显式节点 `root`；每一段先按原样定位、
再去掉冠词定位（所以地点变量「the inn」找到叫法「the inn」，而不是长出一个「inn」）。作者写的包从不生长（Z-07）：

1. 输入：内核读到的每一段地点文字——地点变量、地点标签、人物标签和事件标签里的地点——按楼层顺序。
2. 预处理（K-R17），多处取第一处（K-R18），在路上取起点（K-R19），再拆成若干段：
   - `·`、`・`、`›`、`>`，以及两边都有空格的连字符（` - `；「Half-Moon Inn」不拆）按从外到内读；
   - 逗号（`,`、`，`）也表示层级：最后一段定位得到、第一段定位不到时，按从内到外读；否则按语言的中心词位置（`first`：从内到外，
     如「Cellar, Guild Hall, Saltmere」；`last`：从外到内）。
3. 每一段去掉包语言的句首冠词。从根往下走：每一段，如果在当前节点的子树里定位得到某个节点，就走到它；否则新建
   `g_<父 id + 这段文字 的 FNV-1a 36 进制>`，`name` 与 `alias` 都是这段文字，再走进去。
4. 上限：每段 1–40 字，根以下最多 6 层，每个聊天最多长 200 个节点；超了的文字就不上图。
5. 确定性：同一个聊天长出同一棵树。长出来的树是存在聊天变量里、可丢弃可重算的缓存（简报规则 4）。包里有节点时什么都不长。

**K-R93 —— 从卡的世界书取地点候选。** 按书和条目的顺序，对卡自己的每个条目：
1. 跳过：内嵌包条目（K-R91）、变量初始化条目（标题里有方括号括起来的 `initvar`）、带我们归属标记的条目、标题超过 40 个字符的，
   以及（规范化后）与某张名册表里的名字相同的标题（K-R41）。
   *I-26：* 名字和键读取时去掉 emoji 和 `{{...}}` 宏（留在开头的「的」之类所有格助词一并去掉）；标题里有 `|` 的是 `职位|姓名`（人，不是地点，其姓名在别处也跳过）；
   分隔符标题（两端是成串的 `=`、`-`、`*`…）和以文档类 emoji 开头的标题（规则、笔记）不是地点；清理后路径相同的两个条目合成一个节点，键合并。
2. 去掉标题开头的一个方括号标签（`[...]`、`［...］`、`【...】`），再按 K-R26 第 2 步的分隔符拆成若干段，从外到内。
3. 满足下面任一条就是地点：最内一段含有内核给包语言的地点词表里的词（`core/vocab.mjs` 的 `PLACE`，每种语言至多 60 个：中文后缀按子串匹配，
   英文名词按整词匹配）；它的某个关键词含这样的词；它的外一段指的是已经成为候选的地点（Z-04，重复到不再增加）。
4. 节点：id 为 `w_` + `fnv36(规范化后的标题)`；`name` 是最内一段；`alias` 是这个名字、去掉冠词的名字（K-R16）和是普通词的关键词
   （1–20 个字符、不是 `/.../` 形状、没有 `*` 或 `?`）；父节点是外一段所指的候选，没有就是根。
5. 候选至多 150 个，多的丢掉（记一条问题 `candidates-limit`）。

只读标题、关键词和 initvar 文本：条目正文一律不读，除这些词表外也不按文字的意思做任何判断（简报规则 8）。

**K-R94 —— 从卡里取变量、人物、开场视图与语言。**
- **vars**：K-R38 的自动发现，实时 `stat_data` 有键就读它，否则读 initvar 条目的形状（`core/yaml-shape.mjs`：JSON，或由映射、序列、标量与注释构成的
  YAML 子集；其他一律当作没有形状）。发现的路径（地点、时刻、时段、日期、着装、声望、物品栏）写进自动包的 `vars`，导出时就带着；
  用户的变量映射仍然优先（K-R38）。
- **entities**：以名字为键、行里有类似地点或人物字段的表就是名册（里面的名字不算地点，K-R93）；名字表示「在场」的那张表成为 `present` 组
  （`members`、`targets` 仍在运行时发现），符合文字或标签槽位（K-R42）的行字段写成带 `x-slot` 的 `fields`。
- **start**（`ui.start`，Z-08）：`locate`（K-R24，没有 `here`）在开场白前 400 个字符里找到的节点；它只决定打开时看哪里，不是当前所在地。首条消息只是个短标记（不足 40 个码点）时，改读第一条更长的备选开场白（I-26）。
- **lang**（Z-09）：取名字、开场白和条目标题里的字母（至少 20 个）：汉字 ≥ 30 % → `zh`；否则假名 ≥ 10 % → `ja`；否则韩文 ≥ 30 % → `ko`；
  否则 `en`；字母不够 → 界面语言。`zh` 与 `en` 之外的语言用 `en` 内核词表（K-R07）。

**K-R95 —— 自动包。** 没有别的来源给出包时，宿主按卡造一个（`deriveAutoPack`）：`{ id: 'c_' + fnv36(名字 + "\n" + 头像), schema: 2, title: <卡名，截到 80>,
lang, nodes, vars, entities, ui: { start } }`。`nodes` 是一个显式根节点 `root`（以标题命名），加上 K-R93 的候选（挂在它下面，所以长出来的节点总带 `parent`）。
没有 views 块（隐式示意图视图，K-R96）、没有 events 块（中性分类，K-R53）、没有 llm 块。它是外来包（K-R63），要过 `validate2`。它的存储名按 id 走现有的
推导（`core/pack.mjs`）。造出来的包与长出来的节点是可丢弃的缓存，放在包的聊天变量里 ASCII 键 `auto` 下：`{ v: 1, fp, pack, grown: [node], seen: [文字] }`，
经根存储的保存写入（绝不写 `stat_data`），而且只在根已经载入之后才写。`fp` 是卡名、头像、排序后的规范化条目标题和排序后的变量形状键路径的 `fnv36`：
`fp` 相同就原样用缓存里的包，否则重新造（节点 id 是标题的哈希，没变的地点保持原 id），父节点还在的长出节点保留。注入的包带 `rev: 1` 和 `fp`。

*生长。* K-R26 只对自动包运行（Z-07），在造出来的加长出来的节点上：宿主读到的每一段地点文字——地点变量（记在最新一楼）、地点标签、人物与事件标签里的地点——
按楼层顺序，每段文字只处理一次（`seen`，至多 400 条）。新节点进 `auto.grown`；集合变了，宿主重建事件地理，并发出 `eden-map:pack`
`{ manifest, rev + 1, source: 'auto', trust: 'foreign' }`；查看器按外来包再校验一遍、投影并重画（§4.6）。*重算。* 载入聊天时 `auto.grown` 不存在就从零重建
（`recomputeGrowth`，取扫描窗口里的楼层）；存在就直接用，并把实时与重算不一致的节点数记为漂移计数（绝不悄悄修复）。同样的文字，实时生长与重算得到同样的节点（测法同 K-R75）。

### 3.10 上限与稳定引用

**K-R27 —— 上限。** 最多 5000 个节点；每个节点最多 64 个强叫法、256 个弱词（第一个包的宅邸节点有 153 个）；每个词 1–60 字；
一段文字最多扫前 400 字、保留 256 处命中（K-R20）。实现时每棵树只建一次词表，并缓存定位结果。外来包还有更多上限（K-R66）。

**K-R28 —— 按节点 id 引用。** 聊天数据、藏物、协议消息、日志一律用名为 `node` 的字段写节点 id 来指地点。v1 的 `map`、`marker` 字段在 S10 之前照收。

**K-R29 —— describe()。** `map/core/nodes.mjs` 提供 `describe(tree, views)` → `{ nodes, depth, types, grown, views }`，给探针和自检用，
和其他核心模块一样（`depth` = 最深节点的深度）。

### 3.11 v1 的 `here.mjs` 只是一个特例

v1 按固定的六级解析。改写成节点后，每一级都是树上的一类节点，每张 v1 词表都变成强叫法或弱词；原来的级别先后，自然由 K-R20–K-R22 推出来：

| v1 级别 | v1 的词 | v2 节点与词表 | 为什么先后不变 |
|---|---|---|---|
| 1 宅邸房间 | 宅邸图的房间词（+ 房间平面） | 宅邸节点的弱词；有房间平面时，是各房间节点，词都算弱词 | 弱词能细化宅邸，遇到不相干的名字就让位（K-R22） |
| 2 宅邸区域 / 整座宅邸 | 区域词；宅邸本身的叫法 | 区域词：宅邸节点的弱词；本身的叫法：它的强叫法 | 同上 |
| 3 地标 | 标记名、英文名、别名 | 挂在所在层下面的地标节点 | 比层更深（K-R21） |
| 4 层或大区 | 层名、副标题、大区词 | 层节点的强叫法 | 比分组更深 |
| 5 分组或世界地名 | 分组标题；世界图的地点、封地、国家 | 分组节点（与它的世界地点合并）和世界节点的强叫法 | 浅 |
| 6 认不出 | 泛称表挡住地标 | 根的弱词 → `null` | K-R16 |

用一个草稿原型（§3.5 的每条规则，包括整词边界、预处理、移除根弱词、中心词平局规则）加附录 A 的兼容转换核对过：
`tests/here.test.mjs` 与 `tests/card_spec.test.mjs` 里每个不同的输入，落到的节点都和 v1 一样（附录 A.9 列出只有「报告的词」
不同的两条，以及 S3 的全量对拍要列入白名单的几类有意差异）。

## 4. views

### 4.1 种类

**K-R30 —— 四种视图。** `tiles`（DZI 瓦片金字塔）、`image`（一张图，不用切片；特别大的图仍建议用 `tools/make_dzi.py` 切）、
`schematic`（自动排布这个节点的子树，不要坐标）、`model3d`（通用三维查看器的清单）。

### 4.2 坐标系与位置

**K-R31 —— 坐标系与 `at`。** `tiles` 和 `image`：x 向右、y 向下，各按图片宽 / 高取 0..1（即 v1 的 `nx`、`ny`）；`r` 是宽度的比例；
可选的 `extent: [宽, 高]`（米）给出比例尺。`model3d`：清单里模型自己的单位（米；x 东、y 北、z 上）。`schematic`：没有坐标系。
节点的 `at` 写了 `at.view` 时按那个视图读（它必须是某个祖先的主视图），否则按「最近一个主视图带坐标系的祖先」的坐标系来读；
节点自己的视图从不决定它自己在哪。编辑器总是写上 `at.view`，这样以后给中间某个节点加了图，下面节点的坐标也不会悄悄换了参照。

**K-R32 —— 锚点与区域表。** 视图可以带一张区域表：内联的 `[{ id, at | poly }]`、一个文件、一份 schema 1 的点位文件
（`markers[]` 里有 `id`、`nx`、`ny`、`r`），或三维清单里的热点。取位置的顺序：`at` → `anchor` → 区域表里 id 等于节点 id 的那一项 → 没有。
没有位置的节点照样列出，画在坐标系中心附近一个固定的点，标「位置不详」；示意图则自动排布它。

### 4.3 把视图挂到节点上

**K-R33 —— 节点有哪些视图。** 先看 `node.view`（一个 id 或一组，第一个为主），没有就看 `views[<节点 id>]`，再没有就没有。
几个节点可以共用一个视图（一组建筑共用一个三维模型）。视图的 `open` 说明它什么时候打开：`locate`（缺省）= 这个节点是目标时就打开；
`enter` = 只有用户「进入」这个节点时才打开（比如地标的三维模型：定位到这个地标时，仍然在它所在的地图上显示）。

### 4.4 查看器对一个节点显示什么

**K-R34 —— 选视图的规则。** 对来自定位（或导航）的目标节点 N：
1. N 的主视图是 `open: locate` → 打开它。
2. 否则 N 写了 `enter` → 对那个子节点套用这几条。
3. 否则打开 N 最近一个「主视图带坐标系」的祖先的视图（也就是 `positionOf` 用的那个），没有就打开最近一个有任何视图的祖先的视图，
   再没有就打开根的示意图。

结果是 `{ view, owner, kind, focus }`，`focus` = N；N 在那个视图里没有位置时，查看器改为聚焦 N 在那里有位置的最深祖先。「进入」
一个节点（双击或点进入按钮）时，对它套用第 1–2 条，不管 `open` 是什么。

**K-R35 —— 层切换条。** 打开的视图属于节点 V 时，切换条给出：V 自己或它最近的、在 `ui.levels` 里有条目的祖先 L 的 `ui.levels[L]`；
没有这样的条目时，给 V 的父节点下所有主视图是 `tiles` 或 `image` 的子节点，按声明顺序。至少两个时才显示。

### 4.5 专用页面

**K-R36 —— 包里不许带代码。** `model3d` 用通用查看器。`x-page`（包自己的 HTML 页面）只作为旧写法，留给随引擎发布的那一个页面；
所有外来包里的 `x-page` 一律忽略，外来的 schema 1 包经 compat 转出来的也一样（K-R63）。这是设计规则，不请你拍板：卡里带的页面
等于在酒馆页面上跑任意代码。

**K-R104 —— 3D 场景清单的 schema。** `map/data/schema/v2/scene3d.schema.json` 是通用 3D 查看器清单的 v2 schema（文件 `map/estate/model/manifest.json` 与每个 `map/props/<id>/manifest.json`；K-R64 许下的）。它依 `core/scene3d-manifest.mjs` 写成：`id` 与 `glb` 必填，`glb` 是 `"x.glb"`、`{ std, low? }` 或 `{ <部件>: { std, low? } }`（地标的旧写法 `glb` 加 `glb_low` 也认），`floors` 是字符串或 `{ id }`，`hotspots` 是带 `id` 的对象，`budget` / `budgets`，`license` / `credit`，`data` = `{ rooms?, zones?, galleries? }`（相对清单的路径），`flows[].color` 是 `#rrggbb`；未知字段保留（`additionalProperties: true`，这个格式一向如此）。`tools/check_pack.py` 用它和核心模块的 `validate` 检查每一份随仓清单；不合格的只报告、不改。

**K-R131 —— 房间类别作为设定包数据。** 3D 清单可带 `room_kinds: { <kind>: { color: "#rrggbb", label, rank?: 1 | 2 | 3, i18n?: { <lang>: { label } } } }`：该类别每间房的底板颜色，以及它在剖切视图色标与房间卡上的名字（有语言条目取语言条目，否则取 `label`；`rank` 是该类别房间标注的优先级，1 最先，缺省 2）。类别 id 符合 `^[a-z][a-z0-9_]{0,63}$`，颜色运行时用 `recheck.hex` 复核，名字是纯文本、只经 `textContent` 上页（K-R64）。房间用了而表里没有的类别：生成一个颜色（`core/kind-palette.mjs`：八个颜色，在两种主题底色上都至少 3:1，在正常视觉与红色盲、绿色盲、蓝色盲模拟下两两至少相距 20，按类别 id 的稳定哈希挑选），名字就是类别 id。查看器不再自带类别表。`rooms.json`（清单的 `data.rooms`，`map/data/schema/v2/rooms.schema.json`）列 `floors: [{ id, name?, z }]` 与 `rooms: [{ name, node, floor, kind, area?, note?, poly }]`；`node` 是该房间在设定包节点树里的 id（同名房间可共用一个节点），房间卡、人物头像与房间列表按节点 id 对账，名字只作兜底。清单的 `data.extras` 可指向一个可选的包文件，里面有 `room_alias`（搜索时认房间的叫法）、`sub_rooms`（房间里的一个热点）与 `vehicles`（画出来的几件道具及其卡文字）；3D 页自己一个也不写。

**LEGEND-1 修订（D35，K-R131）：**只有 3D 清单写了 `"x-kind-plates": true`（默认 false，第一个包不开）时，类别颜色才会在剖切视图里画成半透明的楼面色块（和逐房间的边线）。不开时，悬停 / 选中的高亮就是房间唯一的边界，不再有色标，房间卡上也没有颜色小块；`room_kinds` 仍是标签和优先级的数据。

**K-R132 —— 建筑的名字。** 3D 清单可带 `building: { title, subtitle?, summary?, i18n?: { <lang>: { title?, subtitle?, summary? } } }`：查看器显示的标题、副标题与一句话简介（外壳的无障碍名字、建筑的卡）。楼层名字是现有 K-R104 `floors[]` 各项上的 `label` 与 `i18n`；`building.floors` 键会被 schema 拒绝（一份列表、一个位置）。没有这个块时，查看器说「Building」、不显示副标题与简介、用楼层 id 当名字。所有文字都是纯文本、用 `textContent` 设置。（地标清单里的 `building: { min, max }` 是它的包围盒，由 `props/viewer3d.html` 读取，不是这个块。）可选的 `view.ext = { target: [x, y, z], size: [w, d, h] }` 以 layout 米给外观视图取景；没有时用模型包围盒。

**K-R133 —— 纵深通道不移动叠加物（TIER-1）。** 视图的纵深数据（`x-depth`、`channels.*`）只能改标签不透明度和雾；画在底图上的叠加物（图钉、标签、轮廓）不相对底图移动。`parallax` 通道只属于屏幕固定的云层。时段色调跟随实际显示的底图：备用底图（`x-alt`）开着且没有时段版本时，照常叠当前时段的色调。

**K-R134 —— 一个地点一条记录。** 任何种类的地点（世界地名、地标、建筑、房间、室外区域）都读成同一种记录，由 `core/place-record.mjs` 现场从包自己的文件算出、从不复制：`id`、`name`、`kind`（`site` / `place` / `building` / `room` / `zone`）、包自己的 `type`、`parent`、`sub`、`desc`、`facts`、`access`、`rows`（包另给的标签 / 值行，例如面积）、`media`、`alias`、`floors`（房间）、`wb`（世界书条目 id，由发布物的 `index` 填）。新增节点字段：`facts`（最多 12 条非空字符串）与 `access`（字符串），都可选、纯文本、经 `textContent` 上页。同一节点的几间房合成一条记录（楼层按平面表顺序；表里的词与同义词成为叫法）；节点自己的 `desc`、`facts`、`access` 优先于房间表。玩家的改动（K-R135）逐字段盖在记录上，包自己的记录从不被改。`entryText(record)` 是世界书条目正文的唯一来源：生成器用它写附加书的房间条目（`tools/place_records.mjs` 把记录交给 `tools/build_worldbook_addon.py`），记录卡显示同一段文字。发布物带 `index { <记录 id>: [条目 id] }`，房间条目可带 `strategy.keys_secondary { logic: "and_any", keys }`（通用名加所在建筑的名字）。有文字的房间才有条目；只有名字的记录没有。

**K-R135 —— 玩家在地点上的字段。** `<聊天变量>.自定义.items[<键>]` 保留原有字段（类、名、用途、别名、源），新增 `说明`（字符串，≤ 400 字）、`事实`（最多 12 条、每条 ≤ 120 字）、`基于`（保存时包原文的指纹 `{ name, desc, facts }`；之后不同就标「包里的原文有更新」）、`楼`（保存时的楼层；同一地点上的剧情标签与手动改动按楼层先后，后来的为准）。键是节点 id；旧键（标准名）仍认，树能给出名字后 `migrateKeys` 一次换成 id。`自定义.撤销` 保留最近 20 次改动的前值。本聊天的自定义书是一条常驻索引（只有名字对照，≤ 220 字）加每个有说明、用途或事实的地点一条关键词条目，正文来自同一个 `entryText`、开头一句说明以本聊天为准；关掉同步只是停用条目。意图：`eden-map:place-edit { id, patch }`、`eden-map:place-undo { id? }`。

### 4.6 查看器里的 schema-2 包

**K-R96 —— 打开 schema-2 包。** `core/pack.mjs` 在 `schema: 1` 之外也收 `schema: 2`：schema-2 清单的 `validate` 只查 `id` 与 `title`，`load` 返回带 `schema` 的解析结果，并把清单放在 `v2` 里；查看器（`app/current-pack.mjs`）接着跑 `resolveBlocks`（块文件相对包目录）、`validate2`（只有随引擎发布的包才算可信，即从 `packs/<id>/` 加载的包）与 `withDefaults`。查看器用一份内存里的投影工作，`projectV2(pack, { base })`（`core/pack-v2-view.mjs`，纯函数），形状就是它现在画的注册表；没有任何查看器模块自己读 schema 2，schema-1 的包也从不经过它。
- **隐式视图。** 没有 `views` 块（或为空）的包，在根和每个有子节点的节点上各得一个示意图视图：布局 `tree`，深度 2，`open: locate`。定位到某个节点就打开它父级的示意图并聚焦到它（K-R34 第 3 条）；进入有子节点的节点就打开它自己的。隐式视图从不导出。
- **地图。** 主视图（显式或隐式）种类为 `tiles`、`image` 或 `schematic` 的节点就是一张地图；地图 id 就是节点 id；`start` 是 `ui.start` 对应到它视图的所有者（K-R34），否则取它之上最近的一张地图，再否则取第一张。一张地图是 `{ title: <节点名>, title_en?: <i18n.en.name>, kind: 'points', base, data, view: { extent_m }, markers }`，`extent_m` 取视图的 `extent`，没有就是 `[1600, 1000]`；`markers` 给地图上画出的每个节点一项 `{ name, name_en?, sub?, alias, link? }`（`alias` = 节点的 `alias`、名字与各语言译名；`link` 通到节点自己的地图，有才写）。
- **底图来源。** `tiles` 是包目录下的 DZI 路径（没有 base 时拒绝：卡里的包与文件包；问题码 `view-tiles-no-base`）；`image` 是 `{ type: 'image', url }`，取包目录下的 `src`（没有 base：`view-image-no-base`；`media` 写法留给后面的步骤）；`schematic` 是 `{ type: 'image', url: <生成的图> }`（K-R97）。每条路径在 URL 解析后再查一遍：不许有协议头、绝对路径、上跳（`view-path`，K-R64）。`model3d` 视图暂不投影（问题码 `view-3d-not-shown`，列在自检里）。
- **虚拟点位文件。** `v2/<包 id>/<地图 id>.json` = `{ extent_m, markers: [{ id, nx, ny, r }] }`，有画框的视图按 `positionOf`（K-R31、K-R32；没有位置的节点放在中心附近），示意图按示意图布局。查看器的 JSON 缓存被预先填入这些文件，所以任何取地图数据的模块都原样拿到。
- **运行时。** `makeRuntimeV2(pack, registry)`（`app/nodes-runtime-v2.mjs`）按包自己的树给出 schema-1 运行时的全部读法：地图 id 是投影出的地图，地图自己就是宿主，`parent` 是最近的、本身是地图的祖先，`levels` 按 K-R35 在这些地图上算，`kind` 是主视图的种类，`geo()` 是这棵树的事件地理。`standIn`、`zoneChildren`、`anchorIn` 为空。

**K-R97 —— 示意图布局。** `layoutSchematic(tree, owner, { layout, depth })`（`core/schematic.mjs`）返回 0..1 内的 `{ <节点 id>: { x, y } }`，边距 0.06，确定性（同一棵树画出同一张图）。`tree`（默认）：所有者在 `{ x: 0.5, y: 0.08 }`；后代按层成行，直到 `depth`，一层一行，行距均匀、到 y 0.92 为止；每个节点占的宽度是它子树在深度内的叶子数，父节点居中在子节点上方；一行超过 12 个节点就折成几行等长的行。`list`：按声明顺序排成一列。`grid`：每行 ⌈√n⌉ 个。`radial`：所有者在中央，每层一圈。图 `schematicSvg(layout, tree)` 是 1600 × 1000 单位的 SVG，透明底，每条父子边一条线（两端都在布局里），每个节点一个半径 6 的点，用固定的中性灰；不含文字、不含任何包里的值（Z-11、K-R64），`schematicUrl` 把它编码成 `data:image/svg+xml` 地址。节点名走普通标记，所以搜索、卡片、事件与抽屉和别的地图一样工作。`image` 视图作为单张图打开（不切片），位置是图的比例（K-R31）。

**K-R114 —— 主题示意图。** K-R96 / K-R97 的示意图有一个主题变体。**何时：** 隐式视图（K-R96）布局出的子树至少有 8 个节点且至少 2 个分支（分支 = 所有者的、在布局里还有子节点的孩子），或显式示意图视图带扩展字段 `x-style: "thematic"`（schema 不变；`"plain"` 或缺省 = 今天的图）；否则是朴素图，与 S8-4b 之前逐字节相同。**功能：** 每个分支取其节点名字经内核通用功能词（`core/vocab.mjs` 的 `FUNCTION`，中英，每个功能至多 12 个词）指向最多的那个功能；并列时按功能列表的顺序；都没有则 `other`；这些词是地点种类的名字，绝不是某张卡的。**画面**（`core/thematic.mjs` 的 `thematicModel`、`core/schematic.mjs` 的 `schematicSvg(layout, tree, model?)`；仍是不含任何文字的 SVG data URL）：每个分支其节点位置的凸包，外扩 0.04，以功能色 0.16 填充；分支自己的父子边画成一条彩色线（按分支顺序取 8 色调色板，线宽 6）；其余的边照旧是灰色；枢纽（布局里有子节点的节点）为带深色描边的白色圆环（r 9），叶子为圆点（r 6，取分支线色）。**标签：** 投影出来的标记在虚拟点位文件里带 `rank`（所有者与分支为 1，其他枢纽为 2，叶子为 3；朴素图没有），`app/markers.mjs` 把它写成标记上的 `data-rank`，由交通层的样式决定标签大小（1 级 `--fs-body` 粗体 700，2 级 `--fs-small`，3 级 `--fs-micro` 不透明度 0.85）。不为自动包编造网络（`transit` 图层在那里不适用）；带 `transit` 块的 schema-2 包会像在任何视图上一样把它画在示意图视图上。

**K-R100 —— 编辑模式。** 设置 → 高级里的开关（「编辑模式」，`edenMapEdit`，默认关）打开编辑条和下面的操作；关着时什么都不画。改动记进每个包 id 一份的本机草稿（Z-14）= `{ v: 1, nodes: { <id>: { at?, parent?, alias_add? } }, add: [节点], views: { <id>: 视图 }, media: { <id>: 项 }, attach: { <节点 id>: [media id] }, start? }`（`core/pack-draft.mjs`；文字存在 `edenMap:edit:<包 id>`，图片字节存在图集 IndexedDB 的 `edit:<包 id>` 作用域；草稿里永远没有私有图片）。开关打开期间查看器显示套上草稿的包，套法就是 K-R67 的叠加层合并（叫法取并集、节点其他字段覆盖、图片按 id、没有 views 的包在加了视图后保留原来的隐式视图、`ui.start`）；schema-2 包每次改动后重新投影（`app/pack-live.mjs`）。草稿从不写进聊天、角色卡或世界书；「放弃草稿」把它清空。操作（`app/pack-edit.mjs`）：`move`（在 `tiles` 或 `image` 视图上拖动图钉；写 `at = { x, y, view }`，K-R31）、`reparent`（拒绝节点自己、它的后代和根：造不出环）、`addAlias`（1–60 字，K-R27）、`addPlace`（id 为 `e_<fnv36(名字 + 上级)>`，落在有画面的视图上点的那一点）、`setStart`、`addPicture` 与 `attach`（地点的图片；草稿里只收内嵌图）、`useAsMap`（「用一张图作这里的地图」：图重新编码为 WebP 0.82、长边至多 4096 像素、去掉元数据；节点得到 `views[<id>] = { kind: 'image', media }`，它的子节点当前的示意图位置成为新画面里的第一个 `at`）和 `discard`。schema-1 包（首个包）的版面保持不动：它的图钉不能在查看器里移动或改上级；可以给它的任何地点加图片并导出为叠加层。导出见 K-R98。

## 5. vars

**K-R37 —— 只读。** 路径是卡的 `stat_data` 里的点号路径；MVU 的 `[值, 说明]` 自动拆开。内核从不写 `stat_data`（简报规则 5）。

**K-R38 —— 兜底与自动发现。** 当前地点按固定顺序兜底：MVU 路径 → 最新一楼正文里明写的地点标签 → 表格数据库插件 → 社区预设的状态栏 → 没有。
包里没写某个路径、或在 `stat_data` 里找不到时，内核在 `stat_data` 里（最深 3 层，浅的优先）按本语言的字段名词表（加上 `lexicon.<语言>.fields`）找键名对得上、值的种类也对得上的
（地点、时间、时段、日期是文字；着装是对象；声望是数字；物品栏是对象或列表）。用户在设置「变量映射」里手动选的（按卡存）永远优先。名册表不属于 vars：
它们是 `entities.groups` 的来源（合并成一处，免得同一条路径写两个地方）。

**K-R39 —— 时段。** `periods` 是作者起名的时段，按时间顺序，每段 `{ id, label, start: "HH:MM", words[], dark }`。判定：先拿时段文字
去对各段的 `words`（最长的词赢，再比靠前）；对不上就从时间文字里读出 HH:MM，落在「起点 ≤ 时间 < 下一段起点」的那段（跨午夜回绕）；
都不行就没有时段。缺省四段：`dawn 05:00`、`day 07:00`、`dusk 17:00`、`night 20:00（夜景）`。`dark` 决定夜景效果；`tiles` 和
`image` 视图可以带按时段 id 分的 `variants`（不同时段的底图）。
查看器显示当前时段的那份变体（宿主时钟消息用 `tod` 带时段 id、用 `bands` 按时间顺序带包的时段 `[{ id, dark? }]`；旧宿主没有 `bands` 就按缺省四段）。
地图没有该时段的变体时，取时段顺序上环形距离最近的已登记时段（一天首尾相接）；平手取不属于 `dark` 的，再取靠前的；没有变体、没有当前时段、
或已登记的键都不是该包的时段 = 地图唯一的底图。已显示本时段自己的变体就不再叠本时段色调（`body[data-base-tod]`）；用邻档变体时仍叠本档色调。`core/period-pick.mjs`。

**K-R76 —— 卡内自己的物品表。** `vars.inventory`（可选，点号路径，只读）指出卡的 `stat_data` 里装着玩家物品的那张表；没写就用内核的物品栏词（`EXACT.inventory`：物品栏、背包、……、inventory、backpack、……）找到的字段，前提是它真是卡里的字段；
两样都没有就没有这张表。`cardInventory(stat, path)` 把它读成行 `{ name, qty?, text? }`（最多 100 行，名字 ≤ 60 个码点，说明 ≤ 80）：以物品名为键的对象（数字是数量、字符串是说明、对象取其中第一个数字和第一个字符串），或列表（字符串是名字；对象：按内核名字词找名字字段，
否则取第一个字符串字段，第一个数字当数量）。MVU 的 `[值, 说明]` 自动拆开，`_` 或 `$` 开头的键跳过，从不写回。它以 `eden-map:inv.card = { path, rows }` 送到查看器（没有这张表时为 `null`）。物品页签把它连同其他分组只读地展示出来：抽屉多一个第五页签 `items`（按钮类 `ittab`，在人物与地点之间，保持抽屉打开，回退排在地点页签之后），分四组。*随身* = `carried: true` 的库行；*这里* = 在玩家所在节点的自有行（`carried: false`）与该节点上没被拿走的世界藏物行（隐藏的只有玩家站在那个点上才算）；*其他地点* = 别处的自有行，每个地点一个小标题，地点按码点排序，没有地点的行排最后，归在「未归位」下；*卡内物品栏* = 上一段的行。空组不画；任何一组有行页签就可见，计数是随身行数。「这里」的世界行有一个拿取按钮，发的是与地图标记同一个 `eden-map:loot` 意图；地点能定位的行有飞过去按钮；卡内行没有按钮。名字、地点、说明都只当文本进页面（K-R64）。旧宿主（没有 `stash` 字段）时，旧行当作「不是随身」显示。

**K-R105 —— 场景头与一楼的地点。** `vars.header`（可选）= `{ tag, sep?, fields }`，声明楼层正文可能带的头，形如元素 `<tag>…</tag>`：`tag` 是 1–32 个字母、数字、`_` 或 `-`（不以数字开头），`sep` 是 1–8 个字符的分隔符（默认 `·`，不含 `<` 与换行），`fields` 按块里写的顺序列出 `place`、`date`、`time`（各至多一次，必须有 `place`）。内核不用正则读它：取该楼最后一个 `<tag>` 块，按 `sep` 切开、各段去空白；地点本身可以含 `sep`，所以段数多于字段数时，多出来的段归 `place`，它前后的字段分别从两头数。块没有闭合、只是前几个字母相同的另一个标签、或块里没有地点，都不算头。**一楼**的地点按下面顺序，先中先得：（1）`vars.location` 处的卡变量，条件是这一楼自己的正文里有变量补丁写了这条路径（`<UpdateVariable>` 或 `<JSONPatch>` 块里写着点号路径 `a.b` 对应的 `/a/b`）；（2）这一楼头里的地点，条件是它认得出节点（K-R15、K-R16：与其他所有地点文本同一套定位）；（3）往楼沿用下来的卡变量；（4）K-R38 里更早的兜底（地点标签、表格数据库、预设状态栏）。头里的地点认不出节点就忽略（不造占位）。结果带来源：`patch`、`header`、`mvu`（沿用）或 `none`；宿主把 `header` 作为 moved 事件的地点来源。地图、人物页（玩家自己的地点，「和你在一起」但没写位置的行照抄它）、往楼的拾取地点与注入的状态行都用这同一个地点，所以模型不再更新的变量，不会声明一个与本楼正文相矛盾的地点。没有 `vars.header` 的包、没有头的楼、还认不出节点的宿主，行为与以前完全一样。绝不写回 `stat_data`（K-R37）。

## 6. entities

### 6.1 核心字段（固定）

**K-R40 —— 实体核心字段。** `id`（规整后的名字：空白合并、去首尾，按 `core/roster.mjs normName` 的方式截断，40 个 UTF-16 单位）、`name`、
`node`（这个人所在地点文字的定位结果；认不出为 `null`）、`source`（`mvu`、`chat`、`table-db`、`fallback`、`imagegen`；v1 把最后这个叫 `baibai`）。
派生：`present`（在「在场」来源的组里、被 `source.with` 标出、或和玩家在同一节点）与合并后的别名。

### 6.2 分组与来源

**K-R41 —— 分组。** `groups[]` 按显示顺序：`{ id, label, source, fallback? }`，其中 `source = { mvu?, name?, place?, with?, present?, tags? }`：
- `mvu` 是一张表的点号路径：以名字为键的对象，或者每行一个对象的数组（名字在 `name` 指定的字段里；缺省按内核的名字词表自动发现）；
- `place` 是行里写地点文字的字段（缺省按地点字段词表加 `lexicon.<语言>.fields.location` 自动发现）；
- `with` 是行里的一个字段，它的值为「是」（`true`、非零数字、或内核「是」词表 / `lexicon.<语言>.present` 里的词）时，这个人和玩家在一起；
  `present: true` 表示整组都和玩家在一起；
- `tags: true` 把聊天里的人物标签也并进来；`fallback` 是包自带的行，直到有实时来源出现同一个人为止。

没写分组时内核自己发现（K-06 待定）：缺省只有「以名字为键、每行是带位置或身份类字段的对象」的表才成组，组名就是表的键名，其余的表可以在设置里打开；
键名对得上内核「在场」词表的那张是在场组；人物标签自成一组。

### 6.3 属性字段

**K-R42 —— 四种字段。** `fields[]` 按显示顺序：`{ field, label?, kind, min?, max?, ladder?, scan?, show? }`。`field` 是来源行里的键，照抄卡。
`fieldValue(def, row)` 读整行，按种类返回（值缺失或读不懂时为 `null`）：
- `text`：文字，截到 80 字；默认放在「更多资料」里。
- `tag`：小标签，由文字、数字或是 / 否得到的短文字。
- `gauge`：`{ value, min, max, band? }`——数值夹在 `min..max`（缺省 0 与 100），画成进度条；`ladder` = 分档 `[{ up_to, label }]`，
  `band` 是第一个 `up_to` ≥ 数值的那档的名字。
- `ladder`：`{ index, label }`——从低到高的阶梯 `[{ label, match[] }]`；值先按名字或 `match` 词完全相同匹配，再按包含（最长的）匹配，
  比较的都是预处理后的形式（K-R17）。`scan: true` 时字段缺失就去这一行的其他文字里找。
- `show`：`subtitle`、`chip`、`detail` 或 `hidden`；缺省文字放 `detail`，其余放 `chip`。
没写字段时，内核按本语言词表自动发现一个「身份」类字段当副标题、一个「进度」类字段当小标签。字段可以带 `x-slot`（K-R69），占用查看器人物卡行的一个名册槽位
（`stage`、`grade`、`core`、`code`、`social`、`height`、`weight`、`known`、`accessory`、`tier`）；没有声明字段的槽位，内核按词表在行里发现，设置里的「变量映射」两者都能覆盖。

### 6.4 头像

**K-R43 —— 头像来源。** `avatar.from` 列出允许的来源：`card-script`（卡自带脚本里的立绘表）、`card-storage`（卡自己的界面写进本机存储的键，只读：
`storage.index`、带 `{name}` 的 `storage.per_name`）、`imagegen`（可选的画图扩展的立绘库）。缺省只有 `imagegen`。包不能放宽的内核规则：
只收 https、只收图片类型、不带查询串，而且用户的开关能一键关掉所有远程头像。`hosts` 列出 `card-script` 立绘允许的「域名[/路径前缀]」：
域名必须带点、必须和网址的域名完全相同，路径前缀在 `/` 处结束。`require` 列出立绘网址必须包含的路径片段。列表写法：带路径前缀的 `hosts` 条目放行的网址里，必须出现其中一个
（把共用图床限定在作者自己的目录，K-R69）。表写法（2026-10-01 修订，I-18）：`{ "<域名前缀>": ["<片段>", …] }`——只有落在该域名前缀下的网址
需要其中一个片段，别的域名不受约束，所以某个图床的目录规则不会误伤放在另一个图床上的立绘。`deny` 列出永不加载的路径片段。存储键不能以内核保留的前缀开头
（`spatial`、随引擎发布的包的旧前缀、宿主自己的键）。

### 6.5 多来源优先级（固定）

**K-R44 —— 优先级。** 逐个字段比：`mvu` > `chat` > `table-db` > `fallback` > `imagegen`，有非空值的最高来源胜出；标签取并集；
别名合并；`imagegen` 只补空缺。包不能改这个顺序。

### 6.6 媒体来源

**K-R106 —— 包声明的媒体来源。** `entities.gallery`（可选，每包一个）让查看器去读卡自己的脚本里已经带着的一张图片表，并声明模型在聊天里写的、指向这张表的标记的语法。两样都是数据：包不写正则，也不复制任何图片或地址。字段：`from`（`card-script`）、`path`（进卡脚本数据的点号路径，即 `getCharData('current').data.extensions`；`*` 走遍列表的每一项，最多 8 段）、`name`、`cover?`、`sets`（表的每一行里放角色名、封面地址、以及对象 `{ 类别: [地址] }` 的字段名）、`tag` = `{ fields?, open?, close?, categories, digits? }`、`require?`、`deny?`、`id?`。语法的槽位由内核提供：一个标记就是 `name`、`category`、`number` 三个字段，按 `tag.fields` 的顺序（缺省即这个顺序）依次写出，每个字段用 `open` / `close` 包起来（缺省 `[` 与 `]`，各是一个非字母数字字符）。`category` 必须恰好是 `categories` 里的一个词（1–12 个、每个至多 20 字符，同时是显示顺序）；`number` 是 1 到 `digits` 位（缺省 4，至多 6）ASCII 数字；`name` 是直到结束符之前的任何文字，去空白后 1–40 字符、不含换行。名字本身是类别词的不算标记；不合语法的文字不算标记，原样放着。代码块或引文里的标记照算（它们就是文字）。内核用扫描器（`core/gallery-spec.mjs`）而不是正则来编译这套语法。标记里的编号从 1 数起，在该角色这一类别的列表上回绕（`list[(编号 - 1) mod 长度]`）；表里没有的名字或类别不算场景。

地址：表在运行时从卡里读（只读，每个聊天一次，什么都不落盘）。列表保留位置：没通过检查的地址原位变成空，所以标记里的编号仍按卡自己的列表数。允许的域名取包的 `entities.avatar.hosts`（K-R43：https、图片类型、不带查询串，域名相等并遵守路径前缀）；`entities.gallery.require` 与 `deny` 是这个来源自己的目录规则（头像的 `require`、`deny` 是立绘规则，不约束图鉴）。宿主发表之前检查每个地址；查看器在地址进 `src` 属性之前再查一遍（立绘形状检查之后再过 `galleryUrlOk`）；文字只经 `textContent` 进页面。没有 `entities.avatar.hosts` 或没有 `entities.gallery` 的包什么都不显示。

画什么，全部在每一轮从聊天楼层的正文重算（什么都不存，聊天变量与本机存储不动；重算与上一次逐项一致）：（1）人物卡多一节，按类别分组（卡里的图，打开某一组时才请求缩略图，不对任何类别做过滤）；（2）聊天里的每个标记解析成 `{ 楼, 地点, 角色, 地址 }`：一楼的地点就是 K-R105 的那一楼地点（`MVUBridge.floorPlace`：它自己的补丁，然后认得出节点的头，然后沿用的变量），节点由查看器用与其他所有地点文本相同的定位器认出（K-R15、K-R16），角色是名字、别名或短名（中点之前）与表里名字相符的名册行（短名有歧义则都不算）；地点卡列出「此处的场景」，人物卡按楼序列出这个人的场景；（3）从不往聊天消息里插图（卡自己的脚本做这件事）。一个开关（`edenMapGallery`，默认开，登记在 `core/storage.mjs`）关掉整个来源：不读、不发、不画。这一节的标签是内核键 `ch.gal`（中性措辞）；第一个包经清单 `strings` 覆盖它。线上消息：`eden-map:media`（宿主 → 查看器：`on`、`id`、`cats`、表变化时才带的 `chars`、`scenes`）与 `eden-map:media-ask`（查看器 → 宿主：再发一遍）。模式：`map/data/schema/v2/entities.schema.json` 的 `gallery` 与 `core/pack-v2-spec.mjs` 的 `entitiesBlock`；profile 带着原始声明（`profile.gallery`）。

## 7. items

**K-R45 —— 世界藏物。** `items.stash[]` 是 `{ id?, name, node, hidden?, note?, dc?, qty? }`（即 `map/core/stash.mjs` 的行结构，只是用 `node`
代替 v1 的 `map` + `marker`）。一行换成 `stash.mjs` 的形状是 `{ map: <节点所在带坐标系视图的主人，没有则 ''>, marker: <节点 id>, place: <节点名>, … }`，
缺省 id 就是 `stash.mjs rowId` 对这行算出的值（`'s'` + `map|marker|place|name` 的 FNV-1a 36 进制）。`hidden`（暗格）让搜索难度 +3；
d20 + 加值 ≥ `dc`（缺省 10）才找到。最多 200 行。

**K-R46 —— 拾取词表。** 内核按语言内置词表（获取动词、体标记、量词、「不是东西」的词、泛指词）和严格度规则：拾取必须「动词 + 具体名词」同时成立
（名词带引号、带量词、是已知物品名——藏物名与身上已有的东西，或者是 2–8 个字的光秃名词，和今天 `core/pickup.mjs` 收的一样）。
包可以按语言增补 `verbs`（普通类）、`verbs_strict`（严格类）、`not_items`，用 `verbs_off` 停用内核动词。句式与永不算的写法见 K-R77。

**K-R47 —— 一个仓库。** 玩家身上的东西存在 `<聊天变量>.stash`（第一个包：`eden_map.stash`，决定 D4）。v1 的旧仓库键和虚拟槽位键在第一次读取时并进来（S6）。
形状见 K-R74。可以从聊天记录重算，从不写进 `stat_data`。

**K-R74 —— 一个藏物库。** 地图知道的每一件东西都存在 `<聊天变量>.stash`（第一个包：`eden_map.stash`；这个键对每个包都叫 `stash`，ASCII）。形状：`{ v: 1, items: { <id>: Row }, seq, slot, removed, since, upTo, from? }`，
`Row = { name（1–60）, place（≤ 60，'' = 无）, map（≤ 40）, node（'' = 没解析出）, hidden, note?（≤ 200）, qty?（2–999）, src, carried, msgIndex, mark? }`。`src` 说这行从哪来：`text`（正文里认出的拾取）、`map`（玩家拿走的藏物表行）、`api`（扩展接口）、
`legacy`（来源认不出的 v1 旧行）；`carried` 说玩家是否带在身上（缺省：`text` 与 `map` 为真，其余为假）。只有物品页签读 `carried`：地点卡的「存放」行与注入的摘要行仍按地点列出每一行。
`mark`（仅 text 行）是这行所来自的那条消息正文的哈希。`slot` 是 W12 虚拟槽位，地图自己对已捕获拾取的账：`{ name, path, virtual, msgIndex, facts: { <id>: { name, msgIndex, place? } } }`；`removed` 存经接口删掉的 text 行的墓碑
（最多 200 条，最旧的先丢；同一件东西再次拾取时墓碑保留，它是这次删除的唯一记录）。id 沿用 v1（`i<n>`、藏物表行的 id、由名字混出的 id）：三维页的「已拿走」清单与藏物发光靠它们。
**迁移**只跑一次：聊天变量没有 `stash` 且有旧键之一时（旧键名是 `tavern/stash-store.mjs` 里的常量，只读，S10 随迁移一起删）：每个 v1 行变成一行（id 是名字混出的 id 则 `src` 为 `text`，是藏物表 id 则 `map`，否则 `legacy`），槽位逐键映射，
`since` 是新库第一次扫描的那一楼，`from` 记下旧键。旧键从不被写或删：根是整块替换的，所以每次保存都把它们的值原样带回去，从没有过旧键的聊天也不会多出它们。注入的摘要行和槽位行对同样的行与 v1 逐字相同。

**K-R77 —— 拾取句式。** 两类动词。*普通类*：内核的中文动词与 `picks up`、`picked up`、`grabs`、`grabbed`、`pockets`、`pocketed`；宾语要带引号、带量词、是已知物品名，或是 2–8 个字且不是泛指词的光秃名词。*严格类*：`获得`、`得到`、`拿取` 与 `obtains`、`obtained`、`gets`、`got`、`takes`、`took`、`receives`、`received`、`acquires`、`acquired`；宾语必须带引号、带量词或是已知物品名（英文：只认引号或已知名）；处置式 `把` / `将` + 名词 + `拿取` 与普通类一样算。中文三种形状只认中文动词；英文形状是动词 + 可选限定词（`a`、`an`、`the`、`some`、`his`、`her`、`their`、`my`、`your`、`its`）+ 以字母开头的名字，名字开头的限定词会被剥掉（O-1）。**永不算的句式**，对每个动词、每一类、每一条命中逐条检查；分句 = 两个句末之间的一段（`。！？；…!?;`、换行、后面跟空格的句点）：动词前 4 个字（英文 3 个词）内有否定词（`没有 没能 无法 不能 没 未 不 别`；`not`、`n't`、`never`、`no longer`），但 `不由得 不由 不禁 不得不 不一会 不久 不料 不觉 不住` 里的 `不` 除外；疑问（分句以 `？` / `?` 结束，或以 `吗 呢 么` 结尾，或以 `是否 能否 有没有 要不要` 开头）；对话（动词严格落在 `“…”`、`「…」`、`『…』` 或成对的 `"` 之内；紧跟动词开的引号是引号名形，不算）；分句里动词前有意图或条件词（`想 要 打算 准备 试图 企图 希望 如果 要是 假如 若`；`want to`、`try to`、`if`、`would`、`will`）；`得到` 前一个字是「能做」类动词字（`看听想做找买办猜闻感觉等赶追吃用见`）；`获得` 后跟 `者` 或 `感`；宾语在不是东西的词表里（内核中英文词表加包的 `not_items`）。这些规则只决定什么算拾取，从不隐藏或改写聊天正文。包的词都是字面字符串（不是正则）：`verbs` 并入普通类，`verbs_strict` 并入严格类，`verbs_off` 从两类里去掉内核动词，`not_items` 扩充词表。宿主从 `profile.pickup`（包的 `items.pickup` 跨语言取并集；schema-1 包的叠加层可带 `items.pickup`，它是叠加层 `items` 块里唯一被读的部分：按语言取并集，坏列表是 `overlay-items-invalid`，其他键是 `overlay-items-ignored`）读到它们，传给 `scan(text, { vocab })`；编译好的正则按词表记一份。

**K-R78 —— 结算写入路径。** 结算审计的 npc 与事件两个域写进地图自己的聊天变量，从不写 `stat_data`：`<聊天变量>.ledger = { npc: { <名字>: { place, node, msgIndex, src: 'routine' } }, events: { <id>: { type, level, node, msgIndex } } }`，各最多 200 条（按 `msgIndex` 丢最旧的）。npc 事实是本轮日程的位置（权威 `verified`），只取属于某个名册组的人；已落盘视图是 MVU 在场名册的地点并上 `ledger.npc`，名册里没有地点的人是空洞；审计只补空洞（已有地点的人绝不覆盖）。事件事实是解析出的聊天事件（权威 `committed`），以 id 为键；id 不在账里就出补丁（类型已由包的事件块解析，K-R50，所以审计用选项 `anyEventType` 接受任何非空类型）。补丁经结算闸门，与藏物库同一条保存路径。整条路径只在宿主开关 `edenMapLedgerWrite` 打开时运行（默认关，在设置 → TavernHelper）；关着时不产生事实、不读取，聊天也不会得到 `ledger` 键。账是可丢的缓存；把已结算的事件与 npc 位置画出来是后面的步骤。

**K-R75 —— 对账。** 库是聊天的缓存。实时折叠（`step`）每条消息只扫一次，从 `since` 起、绝不扫它之前的楼（最新一楼每轮再扫一遍，所以它被 swipe 也看得见）；某条消息的正文自它的行生成以来变了就重放
（它的 text 行与槽位事实按新正文重建；别的通道拥有的行不动）；拾取变成 text 行，除非这件东西已在库里，或在这条消息当时或之后被删过。`recompute(messages, { since, actions })` 从零重建：先是不属于任何消息的动作，
再按顺序每条消息，后接记在它那里的动作（地图拾取、接口写入与删除：`actionsOf(stored)`）。`reconcile(stored, recomputed)` 在两边 id 相同、且逐 id 的 `name, src, carried, msgIndex, qty, hidden, note, mark`（调用方用了同样的地点时再加 `place`）与槽位事实都相同时为 `ok`；
`missing`、`extra`、`changed` 列出差异。偏差只报个数（设置里的自检），绝不悄悄修；`since` 之前的历史不回填。

## 8. events

### 8.1 标签语法（固定）

**K-R48 —— 标签语法永久固定。** 紧凑写法 `⌖<类别>｜<地点>｜<等级>｜<一句话>｜<发布方>`（全角半角竖线都认；发布方可省；等级 0–3，0 = 已平息），
也就是 `⌖类别｜地点｜等级｜一句话｜发布方`。属性写法 `<span data-spatial-event="type=…;place=…;…">`；第一个包的旧属性永远照认，
v1 的中文字段名与英文名（`type`、`place`、`title`、`level`、`status`、`code`、`layer`、`source`、`time`、`scope`、`duration`、`xy`）都收。
代码块里的、以及 `examples` 里的示范原文跳过；每楼最多 `life.per_msg` 条。

### 8.2 分类

**K-R49 —— 只说「是什么」，不说「在哪」。** 事件块只描述事件是什么：`groups[]`（图例顺序）、`types{}`、`fx_presets{}`、`levels[]`、`closed[]`、
`examples[]`、`life`。里面没有层、匹配词、界外名、城区。

**K-R50 —— 类型判定。** 所有比较都用预处理后的形式（K-R17）；一个类型的「名字」包括它的 `label`、各语言的 `i18n.<语言>.label` 和它的 id。
类别文字 → 某个名字或别名与它完全相同的类型；否则它包含哪个类型的名字（最长的，再比位置靠前）；否则它包含哪个别名；否则它等于某个大类的 id
或名字 → 记为该大类颜色的 `other`；否则 `other`。`other` 永远存在，属于 `other` 大类，名字由内核给；它只按「相等」匹配（不按「包含」），认不出的词取它的名字、图标和稀有度（只写了大类名的词仍用该大类的颜色）。

### 8.3 落点与范围

**K-R51 —— 在哪由树决定。** 地点文字（写了 `layer` 字段就把它加在前面）按 K-R24 定位。明写的 `xy`（0..1）覆盖节点在 `scope(节点)` 那张视图里的位置；
`scope`（范围）同样定位，效果覆盖那个节点的整个子树。「附近」的定义：`scope(事件节点) = scope(当前地点)`，其中 `scope(n)` = n 自己或最近祖先里主视图是
`tiles` 或 `image` 的那个，没有就是根；只有附近的、进行中的事件会注入给模型。地点认不出的事件按 K-01。
事件画在节点明写的 `at` 所在的那张地图上（地图上的一个点，例如世界地点、城区），没有就画在 `scope(节点)` 那张地图上；列表里显示的层名是这张地图属主的 `x-layer`，没有就是它的名字。
自己有地图的站点，里面的地点画在那张地图上，站点本身是上一级地图上的一个点（S3-2）。

**K-R52 —— 不过滤内容。** 类别、地点、一句话都按原文解析和显示。认不出的类别记为 `other`；不会因为写了什么而被丢掉。

### 8.4 缺省

**K-R53 —— 中性默认分类。** 没有事件块时，内核用中性大类（治安、天气、政治、民生、冲突、灾害、人物、其他），每类几个类型，名字来自内核字典的 `zh` 和 `en`。具体表（S4-1，`core/events-default.mjs`，名字以中文为底、`i18n.en.label` 给英文，英文名也进 `i18n/en.json` 的 `names`）：治安（巡逻、检查点、案件）、天气（风暴、降雨、高温、寒潮）、政治（政策、选举、会议）、
民生（节庆、集市、公告）、冲突（交锋、骚乱、对峙、突袭）、灾害（火灾、停电、事故、坍塌、洪水）、人物（到访、露面、丑闻）、其他。有事件块但没写 `closed` 的包用内核的关闭词（`DEFAULT_CLOSED`）；没有标签模板时，注入句的标签是 `地图事态`。

**K-R54 —— 寿命缺省。** 按楼层计：`live 7`、`after 20`、`fade 40`、`merge 15`（同类型、同节点 15 楼内再出现 = 同一事件，「同节点」包括地点文字里匹配词没盖住的那部分：「霓虹街」和「霓虹街后巷」是两个事件；节点为 `null` 的事件按同类型、同样的预处理后地点文字算）、`per_msg 3`。
未结束的事件只要还在扫描窗口里就不会因为旧而消失。类型可以用自己的 `life` 覆盖其中任何一项；包的 `events.life` 覆盖所有类型的内核值。

**K-R55 —— 特效积木。** `none`、`glitch`、`flash`、`shake`、`tint`、`pulse`。屏幕类（`glitch`、`flash`、`shake`、`tint`）服从设置「关闭事件屏幕特效」（D11）；
「减少动态效果」时只留 `pulse`。类型用 `fx` 声明自己的特效（内核积木名，或 `fx_presets` 的键）；查看器对任何「类型解析到它」的未结束事件触发该积木——不再看类型名（S4-1）。预设字段：`intensity`（0–1；没写 = 按事件的等级 1–3 定强度）、
`x-messages`（特效持续多少楼；事件自己的 `duration` 优先，缺省 3）。类型的 `x-default-off: true` 让它在列表和地图上默认隐藏，直到用户第一次动图例筛选。

## 9. layers

**K-R56 —— 预留的形状。** `layers[]` 按菜单顺序：`{ id, type, source, slot, applies, style, menu, legend }`。`slot` 是十个固定槽位之一，从下到上：
`base`、`depth-haze`、`fog`、`routes`、`trips`、`events`、`markers`、`labels`、`fx`、`interaction`。`type` 是一种渲染积木
（`point`、`area`、`line`、`label`、`tint`、`particles`、`flow`；S8 加上 `sound`）。其余由 S8 设计，除 `id` 和 `slot` 外每个属性都可能收紧。

**K-R79 —— layers 块。** 一个图层就是一行 `{ id, type?, slot?, source?, data?, filter?, applies?, style?, menu?, legend?, off? }`（schema
`map/data/schema/v2/layers.schema.json`；`_…` 与 `x-…` 键保留，K-R04）。`id` 符合 `^[a-z][a-z0-9_-]{0,31}$`。引擎自带一份内核图层清单
（`core/layer-defaults.mjs` 的 `KERNEL_LAYERS`：17 个视口图层（S8-1）加上 S8-3 的 `nav-ops` 与 `local-props`，各带槽位、kind、order、菜单行与所用的绘制积木，内核代码自己画的 `type` 为 `null`）；
各模块经自己的宣告注册（`app/layer-host.mjs` 的 `declared(id, impl)`），所以注册表里恰好是清单上的事实加模块自己的函数。生效清单 = 内核清单按 id
并上设定包的行（`mergeLayers`，纯函数，`core/layer-spec.mjs`）：id 是内核图层的行是**调整**，只留 `menu`（label、title、`i18n`、`order`、`default`、
`hidden`）、`applies`（与图层自己的代码规则取与）、`legend` 和 `off`（图层仍注册、变为不可见、没有菜单行）；它的 `type`、`slot`、`source`、`style`、
`data`、`filter` 被忽略并记录（`layer-kernel-fixed`），内核图层的默认可见性仍是它自己存的开关。其他 id 是**声明**新图层：需要 `type`、`slot` 和
`source` 或 `data`，否则丢弃（`layer-incomplete`）；重复 id 取第一行（`layer-duplicate`）；`source: "kernel"` 被拒（`layer-source`：内核清单是封闭的）。
菜单顺序：内核行保持内核顺序（10 … 80），除非给了 `menu.order`；新图层的顺序是 `menu.order`，否则 `1000 + 它在数组里的序号`。上限对每个包都一样
（随仓的与外来的；运行时宽容、工具严格，K-R06）：新图层至多 32 个，每层至多 1000 个要素，每个要素至多 2000 个点，每层图例至多 8 行，`style.by`
至多 16 种 kind，不同的 MVU 路径至多 8 条，`file:` 来源至多 256 KB 且 URL 解析后仍在包的 base 之下（K-R64）。样式值使用时再检：颜色是
`#rrggbb`、`#rrggbbaa` 或 K-R58 的令牌名，数字夹到各自范围，图标是内核图标名（`prop:` 图标只给本机图层，S8-3），不合格的丢弃并记录
（`style-value`、`style-unknown`）。没有 `layers` 块的包原样用内核清单。运行时设定包的行以 `RT.layers` 到达查看器（两种 schema 的节点运行时都有）；
启动时 `applyPackLayers` 合并它们，经 `registry.patch` 调整已注册的内核图层；新图层留在 `packLayers`，S8-2 起画出来。`validate2` 用与运行时
同一个 `normLayer` 检查这个块。

**K-R81 —— 来源与要素。** 要素是 `{ id?, view?, at?, node?, pts?, closed?, r?, kind?, label?, i18n? }`：坐标是打开视图宽高的比例（0..1，K-R31）；
`view` 缺省取图层 `applies.views` 里唯一的那个；`node` 要素画在「当前地点」引擎画该节点的地方；既没有可用视图又没有节点的要素被丢弃
（`feature-no-view`）；积木需要自己的几何（`point`、`label`：`at` 或 `node`；`line`、`flow`：至少 2 个点；`area`：至少 3 个点，或 `at` 加 `r`；否则
`feature-geometry`）。`label` 至多 60 个码点，只当文字显示（K-R64）。`source` 是下列之一：缺省且有 `data`，或 `inline`；`file:<path>`（包 base 下一个
`.json` 文件 `{ features }`）；`view:routes`、`view:markers`（打开视图自己的数据文件）；`events`、`people`、`items`、`routine`（实体适配器与日程
已经持有的东西，K-R71、K-R74；不凭空造）；`mvu:<path>` 与 `ops`（宿主送值，S8-3）；`kernel`（只给内核清单）。外来包（K-R63）可用除 `kernel` 外的所有
来源；本机图层（S8-3）不可用 `file:`、`mvu:`、`ops`，id 以 `local-` 开头。`core/layer-spec.mjs` 里的 `parseSource`、`normFeature`、`normLayer`
是唯一实现。

**K-R82 —— applies。** `applies = { views?, kinds?, nodes?, node_types?, periods?, dark?, data?, mvu? }`：`views` 打开的视图 id，`kinds` 打开视图的种类，
`nodes` 打开视图的所属节点（或它的某个祖先），`node_types` 所属节点的类型，`periods` 当前时段带 id（K-R39），`dark` 该时段带是否为暗，`data`
打开的视图上是否至少有一个要素（`point`、`label`、`line`、`area`、`flow` 缺省为真，其他不要求；内核图层不要求），`mvu` 宿主送来的值条件（S8-3）。
给出的每个键都必须满足（与）；列表里任一项满足即可（或；空列表不约束）；缺省或空的 `applies` 处处适用；未知键忽略。`core/layer-spec.mjs` 的
`appliesTo(applies, ctx, type)` 是纯函数；`registry.applicable(id, ctx)` 在没有 `applies` 时返回真，函数返回它的结果，对象走 `appliesTo`。S7
负责菜单行变灰与不适用图层动画的暂停；S8 负责数据形式与求值器。

**K-R83 —— 菜单行与可见性。** `menu = { label, title?, i18n?, order?, default?, hidden? }`：图层菜单由数据驱动（每个带 `menu` 的已注册图层一行，按
`menu.order` 再按注册先后）；行文字先取 `menu.i18n.<lang>`，再取 `menu.label`，没有设定包 label 的内核行用它原有的词典键；文字一律用 `textContent`。
设定包给内核行写的 `label` 或 `title` 替换该行的词典文字。`menu.default`（缺省为真；`sound` 一律为关）是设定包声明的图层在用户切换前的可见性；
用户的选择存在存储键 `edenMapLayers`（一个 JSON 对象，图层 id → `1` / `0`；登记在 `core/storage.mjs`，属主 `app/layer-host.mjs`；S8-2 起读），
与所有键一样由存储服务按包加命名空间。内核图层沿用已有的键。设定包的行应用后，菜单再渲染一次。

**K-R80 —— 绘制积木与样式。** 宣告式图层由内核八种积木之一绘制，由 `type` 决定；包只给几何与样式值。`point`（地图叠加层里的 HTML 元素，屏幕尺寸恒定）与
`label`（文字，`tone` plain | chip，`size` micro | small | body）放在要素的 `at` 或 `node` 处；`line`（`pts`、`closed`）与 `area`（`pts` 闭合，或 `at` + `r`
画圆，`r` 是宽度的比例）每层每视图共用一个 SVG 叠加层，描边不随缩放变粗；`flow`（沿 `pts` 移动、带渐隐尾迹的光点，夜里更亮更长）、`particles`（整个视图上的
内核天气预设）与 `tint`（一次半透明填充）画在图层所在槽位的画布上；`sound` 没有像素（S8-3）。样式键、取值与缺省：`color`（`#rrggbb`、`#rrggbbaa` 或内核颜色
令牌名；缺省 `--accent`）、`opacity` 0..1、`by`（至多 16 个按种类的覆盖）、`size`、`icon`（内核图标名）、`pulse`、`tone`、`width` 0.5..8、`dash`（至多 6 个数）、
`halo`、`badge`（`label` 芯片用要素的颜色填充，K-R110）、`fill` 与 `fill_opacity`、`speed`、`density`、`trail`、`path`（`flow` 同时画自己的折线：一件用户看得见的东西就是一层）、`preset`；每个值运行时都重新检查，
不合格的退回缺省（K-R64）；颜色只经 CSS 自定义属性进样式，画布用从页面解析出的值。包宣告的动画图层在 `prefers-reduced-motion: reduce` 下什么都不画（脉冲变静态）；
省流档把光点和粒子减半，内核自己的车流层与天气层同样如此。这两层与航线层经同一批渲染器绘制（`core/layer-geometry.mjs`、`app/block-canvas.mjs`、
`app/block-overlay.mjs`），由记录调用的测试证明。

**K-R109 —— 路线器。** `core/router.mjs`（纯函数）在 transit 块上做规划。`buildGraph(transit)` 给每个线路区段（`ride`，带线路与分钟数）和每个连接（`link`）各生成一条边，双向，除非 `oneway`；邻接表按声明顺序（先线路，后连接）；另有 `linesAt` 和派生的换乘站（被两条线服务，或被一条线服务并有连接通到另一条线服务的站）。`attach(graph, end, env)` 把一个地点接入网络（`end = { node?, pos? }`，`env = { tree, pos(站点或端点), extent(视图) }`），按顺序、找到站点就停：**at**（同一节点上的站点，0 分钟）、**inside**（最近的祖先节点上的站点）、**within**（后代节点上的站点，全部）、**walk**（仅当有位置：同一视图上步行分钟 `距离_米 × detour / walk_m_per_min` 不超过 `access_max_min` 的站点，由近到远，至多 4 个；视图的 `extent_m` 给出米数）；什么都没找到 = 不在网络上。`planRoute(graph, from, to, { env, modes, src })` 在状态（站点、当前线路、是否已乘过）上做最短路搜索，从虚拟源点（起点候选，代价为接入分钟）到虚拟终点。代价是分钟：乘一段加该区段的分钟；上一条不同的线要加它的 `wait`，路径上已乘过时再加 `options.transfer_min`；连接加它的分钟并让当前线路清空；`modes` 去掉其他方式的乘车与连接边（接入段永远是步行）。平手依次比：总分钟、乘车段数、停靠数、声明顺序，所以同样的输入永远得到同样的路线。直接步行（两端在同一视图上都有位置，且不超过 2 × `access_max_min`）在不更慢时胜出；两端同一节点或一端在另一端里面，或无路可走，得到 `null`。**路线（plan）** 是 `{ v: 1, src: 'user' | 'op', from, to: { node, station, name }, legs: [{ kind: walk | ride | link, mode, line, stops, min }], min, changes, modes, danger }`：同一线路的连续乘车、同一方式的连续连接合并成一段；换乘与等候不是段；`min` 是整分钟（至少 1），`changes` = 乘车段数 − 1，`danger` = 路径上各站所在城区的最高危险等级（站点自己的 `district`，否则在它的节点或祖先上的城区），不知道时为 `null`。`checkPlan(graph, plan, { tree })` 是宿主的复核：站点存在、乘车的停靠在该线路上相邻且方向允许、连接段对得上该方式的连接、各段首尾相接、给出的节点存在；它按网络重算每一分钟，把接入步行限在 `access_max_min`（直接步行限在两倍），名字由树和站点重建，返回重建后的路线或 `null`。`planText(plan, { lang, templates, nameOf, modeLabel, lineName })` 填入包的 `llm.templates.<lang>` 里的 `route_plan`、`route_leg`、`route_danger`（内核缺省在 `KERNEL_TEMPLATES`，中英各一；占位符 `{legs} {min} {changes}`、`{from} {to} {how} {min}`、`{danger}`），各段用 `；` / `; ` 连起来，`danger ≥ 2` 时追加 `route_danger`，永不抛错（缺的名字是 `?`）。`routeOp(op, { graph, locate, here, floor, map, tree })` 校验“建议路线”操作行 `{ to（1 … 40 个字符）, from?（1 … 40）, why?（≤ 60）}`：两端都要能定位到节点（`from` 缺省为当前位置），两个节点要不同且互不包含，包里要有网络；结果带原样的文字、两个节点、`why`、`floor` 与 `map`，否则 `null`。这里没有任何函数碰 DOM、宿主或存储；绘制在 `core/transit-geometry.mjs` 与 `core/thematic.mjs`（S8-4b 接线）。

**K-R113 —— 建议路线。** 宿主在会话期内至多保留 3 条路线建议行（S7 校验过的 `routeOp` 结果，交给 `tavern/route-flow.mjs` 的 `addSuggestions(rows, { floor, map })`；行上盖玩家所在地点的楼层与地图章，20 条消息后以及换聊天时丢弃，与领航员的线索与标注放在同一份状态里），并在 `eden-map:ops` 里以可选字段 `routes` 发出（旧查看器忽略它）。查看器按两个节点规划每一行（`src: 'op'`，位置同用户的计划），在 `route-plan` 上用虚线画出；点它的终点打开「建议路线」卡，写出理由（`why`，只作文字）、计划摘要与「采用这条路线」（`rt.adopt`），采用即变成用户的计划（K-R111）。建议路线永远不进 `{{eden_route}}`、聊天或任何存储。S7 的操作本身（`OP_ROUTE`、它的 DSL 校验与提示词）归 S7；S8-4b 交付路线器 API 与这条送达线。

**K-R130 —— AI 参谋的建议路线（`OP_ROUTE`）。** 后台参谋的受限操作 DSL（`tavern/operation-dsl.mjs`，K-R86 的沙盒）多一个操作 `OP_ROUTE { to, from?, why? }`：`to` 1–40 个字符的字符串（必填），`from` 1–40 个字符的字符串（可选；缺省 = 玩家当前地点），`why` 至多 60 个字符的字符串（可选）；类型或长度不对就丢弃该操作并计数（throw-not-coerce，与其它操作一致）。每条响应**最多保留一个** `OP_ROUTE`，第二个丢弃并计数（`MAX_OPS` 仍为 3）。`why` 复读事态示范原文时同样被丢弃。`apply` 交给宿主 `routes: [{ to, from?, why?, src: 'op' }]`。宿主（`tavern/llm-flow.mjs` 的 `planRoutes`）对每一行调用 `core/router.mjs` 的 `routeOp(row, { graph, locate, here, floor, map, tree })`：通过的结果进入 K-R113 的建议存储（至多 3 条，20 条消息后过期，经 `eden-map:ops.routes` 发出，由 `route-plan` 画成虚线，「采用这条路线」即采用）；路由器放不下的行在参谋账本里计为丢弃；包没有交通网时什么都不画，`why` 文字并入参谋的提示。这一行从不写到任何地方。参谋的系统提示词在操作清单里写出该操作并多一行说明（`- OP_ROUTE {to, from?, why?}：建议的路线；地点必须用输入里出现过的写法`）；这一行只送到用户自己的端点。

## 10. ui 与 llm

### 10.1 ui

**K-R57 —— 文案。** `ui.strings.<语言>.<i18n 键>` 覆盖该语言的内核字典（v1 的 `键@en` 写法变成 `strings.en.键`）。`ui` 里还有：`start`（最先显示的节点，缺省根）、
`tabs`（`places`、`events`、`characters`、`items` 的子集与顺序；缺省有数据的都显示）、`legend`（节点类型 → 名字、内核图标）、`levels`（K-R35）。
受保护的键不能覆盖：同意开关、远程图片开关、隐私开关以及自检的文案（S7 公布清单）。

**K-R58 —— 主题。** `theme.accent` 加上 `theme.tokens` 覆盖，只收内核的颜色、圆角、字号令牌（`--accent*`、`--ink*`、`--bg*`、`--surface*`、
`--line*`、`--muted`、`--gold`、`--ok`、`--alert`、`--on-*`、`--map-label-*`、`--glow*`、`--focus`、`--r-*`、`--fs-*`；最终清单 S7 公布）。
值是 1–4 个用空格隔开的项，每项是：十六进制颜色、只含数字的 `rgb()` / `rgba()` / `hsl()` / `hsla()`、带可选单位（`px`、`rem`、`em`、`%`、
`vh`、`vw`）的数字、关键字，或 `var(--<内核令牌>)`；不收引号、反斜杠、`url(` 和其他函数（K-R64）。

**K-R84 —— 图层的图例行。** `legend = [{ label, desc?, i18n?, kind? }]`（至多 8 行，K-R79）。抽屉的图例页先列包的 `ui.legend` 条目（标记不变），
再按菜单顺序，对每个已登记、可见且适用的图层列一个标题（图层的菜单文字）和它的各行；每行以一枚按图层样式画的小色块开头（`kind` 取 `style.by[kind]`）：
`line` 与 `flow` 是描线，`area` 与 `tint` 是实心方块，`point` 是圆点，`label`、`particles`、`sound` 没有；颜色经 K-R64 复核后用 CSS 自定义属性设置。
图例页在当前视图不是 3D 页、且今天的规则（纵深数据与 `ui.legend` 条目）或至少一行图层图例成立时显示，所以没有图层图例的包看不到任何变化。
图层的可见性或适用性变化、换图时，这一页重建。

**LEGEND-1 修订（D35，K-R84 / P-03）：**抽屉的图例页对所有包都改为按需开启：只有包在 `ui.tabs` 里写了 `legend` 才有（第一个包没有写，它的 `ui.legend` 条目已删除）；没有开启时，图层菜单里的说明（`menu.title`）是图层唯一的解释。

### 10.2 llm

**K-R59 —— 与模型的接口。** `templates.<语言>` 带占位符（events：`{tag} {items}`；event_item：`{place} {source} {type} {severe} {text}`；
state：`{place} {time} {people}`；custom：`{items}`），以及 `worldbook.book` / `worldbook.entries[{ id, name, content, keys?, enabled? }]`。
`templates.<语言>` 还可以带 `route_plan`、`route_leg`、`route_danger`，即计划路线的句子（K-R108、K-R109）。内核保留：注入预算、降级顺序、同意开关、条目的位置 / 深度 / 顺序 / 递归设置，以及「只写我们自己的附加书（K-R05）、只动带我们归属标记的条目」
这条规矩。外来包的文字什么时候生效见 K-08。

**K-R111 —— 规划路线。** *查看器里*（`app/route-plan-view.mjs`、`app/transit-env.mjs`）：地点卡打开时，查看器把当前地点（`#here`）与卡上的地点解析成两端（`{ node, pos }`：树里的节点，以及这个地点画在哪里——从它所在地图的点位文件里经 JSON 缓存读取，所以答案是异步的），运行 `planRoute`，有计划时给卡加一条链接「路线 · 约 {min} 分钟」（`rt.link`）；没有计划就没有链接，也不发消息（总纲规则 6）。选中它（点击或回车）即把计划变成用户的计划（`src: 'user'`），画在 `route-plan` 上，打开计划卡（标题 `<起点> → <终点>`；「约 {min} 分钟 · 换乘 {changes} 次」；逐段列表：线路色的线路徽标、线路或方式名、`起 → 止`、站数与分钟；每次换乘一行；`danger ≥ 2` 时一行「途经危险区域（等级 n）」；「清除路线」），并发出 `eden-map:route-plan { plan }`。用户的计划存在期间位置变化：新位置就是终点（或在终点之内）则清除计划（到达）；否则从新位置到同一终点重新规划，替换并发出；从那里无路则保持原样。宿主发来的 `eden-map:route { plan }` 替换本地计划（以宿主的那份为准；`null` 清除）；没有宿主（独立查看器）时本地计划保留。颜色只在 K-R64 复核之后经自定义属性进入卡片。*消息*（`core/protocol.mjs`）：`eden-map:route-plan`（查看器→宿主，`plan: object?`：用户选定了一个计划，`null` 表示清除）与 `eden-map:route`（宿主→查看器，`plan: object?`：宿主持有的计划）。*宿主*（`tavern/route-flow.mjs`，仅会话期，不持久化，不写聊天、聊天变量、`stat_data` 或世界书）：收到 `eden-map:route-plan`，计划对 `geo.transit` 过 `checkPlan`（K-R109），通过则连同选定时的楼层一起持有，并以重建后的版本回发（分钟与名字由宿主给）；被拒的计划不动已持有的那份（照样回发）；`null` 清除。新位置是计划的终点或在终点之内则清除，换聊天也清除，超过 20 条消息的计划同样清除。`eden-map:ready` 时把持有的计划再发一次。**`{{eden_route}}`**（仍在原有开关 `edenMapMacros` 之后，缺省关）是最近一段玩家行程 `from → to`（与今天的文字完全一样），持有计划时再加上 ` · `（仅当有行程）与 `planText` 按包的语言写的计划句，由 `llm.templates.<语言>` 的 `route_plan`、`route_leg`、`route_danger` 填充（内核缺省见 K-R109）；没有持有计划时，值与 S8-4b 之前逐字节相同（有测试钉住）。类宏函数在 `tavern/route-flow.mjs`（`eden_here` 与 `eden_fly` 不变）。

**K-R65 —— 外来包写给模型的文字。** 外来包的模板和世界书条目交给宿主之前，内核先把宿主会执行的语法中和掉——这是中和语法，不是过滤内容
（K-R52）：除 `{{user}}`、`{{char}}` 以外的 `{{…}}` 宏一律转义，`<%` 和 `%>` 也转义；形如正则（`/…/标志`）的关键词拒收。上限：16 条、
每条 2000 字、合计 16 000 字；没有关键词的条目（常驻）计入内核的注入预算。

**K-R103 —— 外来包给模型的文字何时生效。** 外来包的 `llm` 块（模板、世界书条目、书名）只有在宿主开关「使用这个包提供的模型文字」对该包打开、
且用户确认过当前文字时才交给宿主：开关在 `edenMapPackLlm` 里存 `{ <包 id>: <llm 块规范 JSON 的 fnv36> }`；存的哈希与包当前的不同，开关读作关，
直到用户在设置里重新确认（被动一行，不弹窗）。默认关。关着时用该包语言的内核模板，不写任何世界书条目。打开后 K-R65 仍然适用。内置包不受影响。
开关经 `eden-map:th` 的 `prefs`（`packLlm`）传递。

## 11. 旧名字

**K-R09 —— 读旧写新。** `legacy` 写这个包在 schema 2 之前用过的名字：`chat_var`、`storage_prefix`、`worldbook_marker`、`worldbook_book`、
`protocol_prefix`、`event_attr`，以及 `write`（`legacy` | `new`，缺省 `new`）。引擎先读新名字，新的为空再读旧名字。`write: new` 时写新名字
（用着用着就迁移了，不需要任何手工迁移）；`write: legacy` 时继续写旧名字。两条永不过期：带新标记或旧标记的世界书条目都算我们的（漏认旧标记会把我们自己的条目当成用户的）；
旧的事件属性永远照解析（它存在历史聊天里）。协议两种前缀都收，只有对方握手报告协议版本 3 之后才发新前缀（S10）。compat-v1 给每一个 v1 包都声明旧名字
并设 `write: legacy`（v1 的世界书标记、协议前缀和事件属性是所有包共用的，不只第一个包），所以 S10 之前什么都不变（决定 D5、a）。`legacy` 只对随引擎发布的包
生效（K-R63）；即便如此，内核保留名单上的名字也一律拒收：`stat_data`、`display_data`、`delta_data`、`schema`，以及别的随引擎发布的包的名字。

## 13. 版本

**K-R61 —— 两个 schema 并存。** `schema: 1` 保持冻结（`docs/pack-schema-v1.md`）；`schema: 2` 就是本契约。`map/core/compat-v1.mjs`
在内存里把 v1 包转成 v2（纯函数、确定性、不写任何文件），所以第一个包和 `town` 不用改文件就能跑；新包直接写 v2。各模块逐个迁到 v2（S2–S6），迁完就只读 v2。

**K-R62 —— 以后加 schema 3。** 不兼容的改动把整个文档的 `schema` 升一级（各块不单独编号），新增 `map/data/schema/v3/`，再加一个纯函数
`migrate2to3(pack)` 让 v2 包继续可用；之后 `schema: 2` 冻结。加可选字段、或把某个 `x-` 字段升格，只要旧读法能忽略它，就仍在 schema 2 内。

**K-R67 —— schema-1 包的 v2 叠加层。** schema-1 包（清单、`maps.json` 等）保持冻结；它需要的 v2 数据放在清单旁边的
`map/packs/<id>/overlay.v2.json`（由清单的 `data.overlay` 声明，查看器和卡内脚本只取声明了的）= `{ "schema": 2, "nodes": [ { id, parent?, alias?, hints?, at?, name?, … } ] }`。
`compat-v1` 的 `fromV1` 以可选参数 `overlay` 接收它，转换完成后按节点 id 合并（`core/overlay-v2.mjs`）：新 id 加到节点列表末尾，必须有 `name`；
已有的 id：`alias` 与 `hints` 取并集（没有显式 `alias` 的已有节点保留它的名字作强名字），其余字段（`parent`、`at`、`name`、`x-…`）覆盖。合并是纯函数、宽容（K-R06）：
不是对象、没有 id、或新增节点没有名字的条目被跳过，记在 `fromV1(…).problems` 里，其余照常。运行时的树（`app/nodes-runtime.mjs`）、当前地点（`app/here-v2.mjs`）
和事件落点在包声明了这个文件时读它；没有的包行为和以前完全一样。`tools/check_pack.py` 校验它（`tools/check_overlay.mjs`：id、名字、父节点、无环、显式 alias 含名字、`at` 是数字）。
首个包的叠加层装的是它的 v1 代码里写死的东西（附录 A.5）：事件的层词（提示词）、带 `at` 的城区节点、城郊与更远的节点，以及世界图的标签 `x-layer`；由 `tools/gen_eden_overlay_v2.mjs` 一次性生成。

**K-R68 —— 叠加层可以带事件块。** 除了 `nodes`，`overlay.v2.json` 还可以带 `events`（v2 事件块，§8.2）和 `llm.templates.<语言>.<键>`（字符串；首个包的注入句标签放在这里）。
这时 `nodes` 可以省略。`fromV1` 把它们合并到从包自己的 `events.json` 转出来的内容之上（`core/overlay-v2.mjs` 的 `applyOverlayEvents`、`applyOverlayLlm`），叠加层优先：
`groups`、`types` 按 id（已有的逐字段覆盖；新大类要有 `label`，新类型要有 `label` 和 `group`），`fx_presets` 按键，`life` 逐字段，`levels` / `closed` / `examples` 整体替换，
其余键（`x-…`）覆盖。和 K-R67 一样宽容：坏的行被跳过并记在 `problems` 里（`overlay-group-invalid`、`overlay-type-incomplete` ……）。`tools/check_overlay.mjs` 还会把合并后的块
过一遍内核自己的 schema（K-R06）。两处都没有事件块的 schema-1 包显示中性分类（K-R53）。

**K-R69 —— 叠加层可以带变量与实体。** `overlay.v2.json` 还可以带 `vars`（§5）和 `entities`（§6），这时 `nodes` 可以省略。`fromV1` 把它们合并到从清单的 `vars` 和名册文件转出来的内容之上
（`core/overlay-v2.mjs` 的 `applyOverlayVars`、`applyOverlayEntities`），叠加层优先：`vars` 的路径键直接覆盖，`periods` 按 id 合并（新时段要有 `start`；列表保持时间顺序）；
`entities.groups` 按 id 合并（新组要有 `label`；`source` 逐键合并，`fallback` 整体替换），`entities.fields` 按 `field`（新字段要有 `kind`），`entities.avatar` 逐键合并（列表整体替换），
其余键覆盖。和 K-R67 一样宽容（`overlay-period-incomplete`、`overlay-group-invalid`、`overlay-field-incomplete` ……）。`tools/check_overlay.mjs` 把合并后的块过一遍内核 schema（K-R06）。
首个包用到两处扩展：字段带 `x-slot`（`stage`、`grade`、`core`、`code`、`social`、`height`、`weight`、`known`、`accessory`、`tier` 之一），绑定到查看器人物卡行与设置「变量映射」用的名册槽位（§6.3）；
`avatar.require`（路径片段）收窄带路径前缀的域名条目：这种条目放行的 `card-script` 立绘，网址里还必须出现其中一个片段（§6.4）。

**K-R70 —— 叠加层可以带 ui 块。** `overlay.v2.json` 可以带 `ui` = `{ theme: { views: { <视图id>: { tokens: {…}, light: {…} } } }, legend: [...], "x-event-level": <视图id> }`。
`tokens` 是该视图打开时（深色主题）的令牌覆盖，`light` 是浅色主题下的；查看器把它们写成一个 `<style>`（`[data-map="<视图id>"]` 与
`.light [data-map="<视图id>"], .light[data-map="<视图id>"]`），所以包可以给自己的每个视图配各自的配色。令牌名和值沿用 K-R58，只放宽一处：`--glow*` 的值可以是逗号分隔的列表，最多 3 组、每组 ≤ 4 项（text-shadow 列表）。
`legend` 条目是 `{ type, label, desc, i18n: { en: { label, desc } } }`（设置 / 抽屉里的图例）；`x-event-level` 指定事态列表兜底用的视图。`fromV1` 把它合并到转出来的内容之上
（`core/overlay-v2.mjs` 的 `applyOverlayUi`）：`views` 按 id，`tokens` / `light` 逐键，`legend` 整体替换，其余键（`x-…`）覆盖。和 K-R67 一样宽容：坏的视图 id 或令牌被丢掉并记入 `problems`
（`overlay-view-invalid`、`overlay-token-invalid`）。查看器运行时用 `recheck`（`core/pack-v2-spec.mjs`：`hex`、`token`、`tokenName`、`id`，匹配精确 schema 模式就返回原值，否则 `null`，K-R64）再查每个 id 和令牌。
`tools/check_overlay.mjs` 把合并后的块过一遍内核 schema（K-R06）。
*S7-2 修订（U-04 B′）：一套外壳。* 分视图的 `tokens` / `light` 不再改外壳（顶栏、弹层、抽屉、设置、卡片）：外壳令牌在每个视图和三维里都一样，只随亮 / 暗和可选的整包外壳强调色
`ui.theme.chrome = { accent, onAccent? }`（六位十六进制；缺 `onAccent` 时引擎按对比度在外壳底色与白色里选更好的；`check_pack` 在两种主题下检查）变化。`ui.theme.views.<视图>` 只写地图空间令牌：
`--map-accent`、`--map-pin`、`--map-select`（来自 `--accent`）、`--map-route`（来自 `--accent-2`）、`--map-tint`（来自 `--bg`）、`--map-glow` / `--map-glow-text`（来自 `--glow` / `--glow-text`）；写成 `--map-*` 的名字原样通过，视图里其余外壳名字被丢弃。
写出的 `<style id="packTheme">` 的选择器和层叠不变。想要某视图以前的样子，在那里写 `--map-*` 即可。

**K-R71 —— 实体协议。** 人、物、事件都是**节点上的实体**：`{ kind: 'person' | 'item' | 'event', id, name, node, place, source, msgIndex, present?, data }`。
`id`：人 = 规范化后的名字（K-R40），物 = 库行或世界藏物行的 id，事件 = 事件 id；`name` 是显示文字，原样；`node` 是节点 id（K-R28）或 `null`（地点不明）；
`place` 是写出来的地点文字（`''` = 没有）；`source` 说明这一行从哪条通道来（人：`mvu`、`chat`、`table-db`、`fallback`、`imagegen`、`routine`、`infer`；事件：`chat`、`op`、`feed`），不带任何出处标注字样；
`msgIndex` 是这条事实在聊天里的消息位置，和消息无关则为 `null`；`present`（只有人）= 和玩家在一起（K-R40）；`data` 是原始行，原样不动。
（1）**纯适配器。** `core/entities.mjs` 把宿主已经发来的行转成实体（`personOf`、`eventOf`），不 import `map/core` 之外的任何东西，并由调用方传入 `nodeOf(文字) -> id | null`
（查看器：K-R24 的定位器；宿主：它的事件地理）。实体是推导出来的，从不以实体的形式存储。（2）**节点按引用。** 一行可以带 `node`；收方自己的树里有这个 id 就用它，否则按 `place` 定位（K-R24：先别名、再提示、最后未知）；
两样都没有就是 `null`。v1 的 `map` / `marker` 字段仍然接受（K-R28）。消息 `eden-map:chars`、`eden-map:events`、`eden-map:stash` 的数组字段里的行可以带 `node`；数组内容不逐项检查（`core/protocol.mjs` 不改字段）。
（3）**同一 id、同一种类只有一个实体**；重复时保留发送方顺序里的第一行。（4）**聊天记录是唯一的真相：** 每个实体都能从聊天楼层和设定包重算出来。（5）**不过滤内容：** 名字和地点按写的原样带着；不认识的类型归「其他」。
`presentAt(entities, here)` = `present` 为真或站在节点 `here` 的实体（地点不明的人从不算「在这里」）：即词汇表里的 PresentEntities。

**K-R72 —— 抽屉页签。** 页签集合由内核固定（K-R02，UI 一行）；抽屉 id 仍是探针用的两字母 id：`events` = `ev`、`characters` = `ch`、`places` = `pl`、`legend` = `lg`（`items` = `it` 在 S6-3 加入）。
`events` 与 `characters` 算「撑住抽屉」（`keepsDrawer`）；选中页签消失时的回退顺序是先 `ev`、再 `ch`。`ui.tabs`（K-R57）给出子集和顺序，来自清单的 `ui` 或叠加层的 `ui` 块（`applyOverlayUi` 把它当作其他键带过来）；
内核不认识的名字忽略，整张表里没有一个认识的名字就用默认顺序。`places` 永远在：`ui.tabs` 没写它时，它排在图例前面（地点卡在它里面）。图例不可排序、永远最后，按它自己的规则显示。
没有 `ui.tabs` 时顺序是 `events`、`characters`、`places`、`legend`。显隐规则就是 v1 的规则，不变：`ev` 在事件列表不空且事态层开着时显示；`ch` 在人物页至少有一个人时显示；`pl` 在任一撑住抽屉的页签显示、或地点卡开着、或有未上图地名时显示；
`lg` 在打开的视图不是三维场景、有纵深数据、且包里有图例条目时显示。三维场景打开时抽屉收起；或者没有任何页签撑住它、又没有卡、手机上没有层胶囊、也没有未上图地名时，抽屉收起。
选中的页签隐藏、或没有选中页签时，按回退顺序选第一个撑住抽屉的页签；关地点卡同样处理并把抽屉收到最低一档。`core/drawer-tabs.mjs` 放纯规则（`KERNEL_TABS`、`tabOrder`、`applyTo`、`firstFallback`）；
`app/tabs.mjs` 是各归属模块提供页签内容的注册表。

**K-R73 —— 按层级显示人物。** 人物页签随打开视图的层级变化。打开的地图在运行时树里至少有一张子地图（任何种类）时层级是**宏观**，否则是**微观**；视图字段 `x-people`（`"macro"` | `"micro"`；v1：`maps.json` 的 `people`，由 compat-v1 像 `clouds` 一样带过来）优先。
没有运行时树、或归属节点不在树里，就没有层级，人物页按平铺画。只有**在场组**分节（其余名册组不变）；每个人只列在第一个收他的分节里：
`here`（在场，或站在玩家所在节点）；仅宏观：视图归属节点的每个子节点一节 `n:<子节点>`，按声明顺序（这个人的节点就是该子节点或在它里面）；`map`（宏观：归属节点本身；微观：归属节点或它里面的任何节点）；
`else`（归属节点子树之外的节点，或树里没有的节点）；`unknown`（没有节点）。空分节不画，剩下不到两节时按平铺画。**什么都不隐藏：** 宏观全部展开；
微观只展开 `here`，其余收成可由用户打开的折叠分节（开合状态会记住）。分节标题从不是列表项；页签的计数、角标、开关、头像和飞过去都不变。

## 14. 设计方的决定与遗留点

### 14.1 设计方已定

| 决定 | 理由 |
|---|---|
| 一个文档；各块内联或拆文件（K-R04、§2.1） | 嵌进卡里要一整块，仓库里要小文件；一份 schema 两种都管 |
| 有序的用数组，查找的用对象（K-R03） | 定位、图例、菜单都靠顺序；引用靠 id |
| `alias` 缺省 = 名字 + 译名；写了就以写的为准，但必须包含名字（除非名字放在弱词里）（K-R15） | 默认零成本，要精确时可控；兼容转换能逐字复现 v1 的词表（改成「只加不减」会让 v1 光秃的英文层名变成强叫法） |
| 不设 `local` 标记、不设泛称表：通用词和泛称都是弱词；挂在两个分支上的强叫法自动变弱词（K-R15、K-R16） | 三个概念合成一个；here.test 的每个输入都和 v1 一致 |
| 根的弱词只盖掉更短的词，从不决定结果（K-R16） | 一个泛称不该让一段带着真正弱词的文字整个认不出 |
| 用空格分词的文字按整词匹配，允许词尾后缀（K-R15） | 「pier」不能匹配「pierced」；中文没有空格，照旧按子串；和 v1 的对照不变 |
| 文字和词用同一个预处理：NFKC、引号、破折号、空白、`&`（K-R17） | 模型输出爱用弯引号和长破折号；不该让作者把每种写法都列一遍 |
| 重叠规则 + 链上计分 + 中心词位置 + 固定的平局顺序（K-R20、K-R21） | 选「能解释最多文字」的答案；平局时取短语的中心词；结果确定 |
| 弱词只能往下细化；平局时取离当前位置近的（K-R22、K-R24） | 含糊的词可以让含糊的答案更具体，但压不过明确的名字；「地窖」指的是这里的地窖 |
| 按来源分信任；`cdn`、`legacy`、`x-page` 只限随引擎发布的包；包里不许带页面代码（K-R36、K-R63） | 一张卡或一个链接不能加载代码、不能接管别的包的数据或卡自己的变量 |
| 包里的文字只以纯文本进页面；样式 / 网址里的值运行时再查一遍（K-R64） | 查看器和酒馆页面同源 |
| 外来包文字里的宿主宏和模板语法要中和掉（K-R65） | 宿主会执行它们；中和的是语法，不是内容 |
| 世界书标记带包 id；书名带内核后缀（K-R05） | 两个包不会互相注销对方的条目；永远不写卡自带的书 |
| 加载顺序：你明确选的最优先（§2.3） | 坏掉的或恶意的内嵌包，你总能换掉 |
| 运行时逐项自愈、修 id（K-R06） | 一个写错的 id 不该把不会写代码的作者的整张地图清空 |
| 视图可以只在「进入」时打开（`open`，K-R33、K-R34） | 定位到地标时不该被它的三维模型顶掉地图（v1 的行为） |
| 层切换条取最近的 `ui.levels` 条目（K-R35） | 第一个包的宅邸与三层保持今天的切换条 |
| 位置可以按值（`at`）也可以按引用（`anchor`，缺省节点 id）（K-R31、K-R32） | v1 的点位文件和三维热点保留自己的几何；兼容转换不用复制坐标 |
| 视图按 id 挂，缺省 `views[<节点 id>]`（K-R33） | 第一个包里一个三维模型由好几栋建筑共用 |
| `enter` 可选；缺省显示最近祖先的视图（K-R34） | 多层的地方保留 v1 行为；其他地方不用写字段 |
| 事件的「附近」= 同一张平面地图，没有就是根（K-R51） | 复现第一个包「同一层」的效果，不用新字段 |
| 署名只放清单（K-R08） | 一处；选包时界面还不存在 |
| 事件类型用 ASCII id + `label` | 英文标识；以前按名字存的筛选照旧按名字匹配 |
| 只有一层的分组与它的世界地点、地图合成一个节点（附录 A） | 「世界地点 = 分组 = 它唯一的地图」本来就是一个地方；少一层 |
| 地标的三维页面是视图，不是节点；测试条目丢掉（附录 A） | 它们是某个地方的画面，不是地方本身 |
| 兼容转换里宅邸的房间和区域是宅邸节点的弱词；真正的房间 / 区域节点随包数据来（附录 A） | 现在就逐字复现 v1，也不依赖三维页面的区域文件 |
| 名册表路径放在 `entities.groups`，不放 `vars` | 一条路径只写一处 |
| 运行时宽松，工具严格（K-R06） | 静默自愈；错误在发布前就被拦下 |
| 途中句式与「写了多处」按语言是内核规则（K-R18、K-R19） | 这是语法，不是内容 |
