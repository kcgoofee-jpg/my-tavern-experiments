# 地点记录：「地点」页、世界书档案与用户编辑（PLACE-1 设计，D44）

状态 2026-10-02：PLACE-1a（数据、生成器、同步）已实现；PLACE-1b（界面）未做。实现时与设计稿的出入：房间条目编号用连字符（`map.room.room-b2-03`，发布编号只许英文点号 / 连字符）；有文字的房间 73 间（含 1 个子房间），生成 72 条房间条目（子房间「衣帽间」与已有的「地点-衣帽间」合并），只有名字的 12 间没有条目；楼层不是节点，上级链里的楼层项 id 写成 `<父 id>#<楼层 id>`；键迁移（旧键 → 节点 id）只给出纯函数 `migrateKeys`，等 PLACE-1b 把各处读键的消费者一起改了再接上。

本文是中文正本（D18），不另出英文版。文中卡里的名字只作例子，引擎和界面里不写任何卡专有词（brief 规则 2.1）。

## 2. 一个地点一条记录

### 2.1 形状

世界地名、层里的地标、建筑、房间、室外区域，统一成一种记录（K-R134，编号以实现时的下一个空号为准）：

| 字段 | 含义 | 例（第一个包） |
|---|---|---|
| `id` | 节点 id；没有节点树的包用标准名 | `room_b2_03` |
| `name` | 显示名 | 惩罚室 |
| `kind` | 种类：`site` / `place` / `building` / `room` / `zone`，外加包的类别标签（K-R131） | `room`，类别「卡」 |
| `parent` | 父记录 id；房间的父是楼层，楼层的父是建筑 | 地下二层 → 伊甸庄园主楼 |
| `sub` | 一行副标题 | 地下二层 · 伊甸家族府邸 |
| `desc` | 说明，1–3 句 | 无窗；重型约束立柱、悬吊禁闭笼…… |
| `facts` | 事实列表，每条一句 | （包里暂无） |
| `access` | 谁能进 | 主人 / 女仆长 / 被带去的人 |
| `rows` | 包另给的标签 / 值行，例如面积 | 面积 40 ㎡ |
| `media` | 图集（K-R101 包图片 id 列表） | — |
| `wb` | 这个地点在附加书里的条目 id（生成器填，见 §4） | `map.room.room_b2_03` |

`name`、`sub`、`desc`、`i18n` 已经是内核节点字段（kernel-schema §3.1）。新增节点字段只有 `facts` 与 `access`，都可选，纯文本，经 `textContent` 上页。

### 2.2 三层来源，后者覆盖前者

1. **包数据**：节点与包文件（下表）。
2. **世界书里的地点散文**：只在包把地点说明写在书里、包数据里没有时才读。第一个包把这些散文迁进包数据（下文「迁移」），所以这一层对它是空的。
3. **本聊天的用户改动**：聊天变量 `<包的聊天变量>.自定义`（第一个包是 `eden_map.自定义`），见 §5。

合并按字段进行：用户只改了 `desc`，其余字段仍取包数据。包数据从不被删或改写。

### 2.3 今天各字段在哪，怎么迁

| 种类 | 今天的位置 | 迁移 |
|---|---|---|
| 世界地名、层里的地标 | `map/data/maps.json` 的标记：`name`、`sub`、`alias`、`link`；另有 42 处的说明在 `map/data/addon_places.json` 的 `text` | `sub` 直接用。`addon_places.json` 的 `text` 成为该地点的 `desc`，文件保留为生成器输入，内容不变。 |
| 建筑 | 3D 清单的 `building { title, subtitle, summary }`（K-R132） | `summary` 成为 `desc`，`subtitle` 成为 `sub`。 |
| 房间 | `map/data/eden_estate_rooms.json`：`name`、`node`、`floor`、`kind`、`area`、`note`、`access`；`extras.json` 的 `sub_rooms`、`room_alias` | `note` 成为 `desc`，`access` 照用，`area` 进 `rows`。同一节点的几间房（例如 14 间同名寝室共用一个节点）合成一条记录。 |
| 室外区域、载具 | `map/estate/model/zones.json` 与 `extras.json` 的 `vehicle_card`，由 3D 页拼成卡片行 | 区域名与说明进记录；3D 页只报「点了哪个」，卡片由记录画。 |
| 剧情事实 | `⌖事实 地点：内容` 标签，由事实结晶（C8）写进附加书 `map.fact.<hash>` 条目 | 记录的 `facts` 分两组显示：包里的事实、剧情里的事实。剧情事实由 `collectFacts` 从聊天楼层重放得到，C8 关着也能显示；写进书仍只在 C8 开着时发生。 |

迁移只换读法，不复制数据：一个纯函数 `map/core/place-record.mjs` 的 `placeRecord(pack, id, custom)` 现场从上面的文件算出记录。查看器画卡片用它，生成器经 node 调同一个函数写世界书条目（与 `tools/node_chain.mjs` 同一做法）。

## 3. 「地点」页显示什么

### 3.1 顺序

1. **当前地点的记录卡。** 选哪一个：
   - 3D：打开着的卡 → 玩家所在的房间（人物位置同一套解析：`hereRes` 的节点落在这栋楼里）→ 这栋楼本身。
   - 2D：打开着的卡 → 「当前位置」图钉所在的地点 → 空态提示「点地图上的地点，这里显示它的介绍」。
2. **上级链，一行**：例「天城 · 上层 · 伊甸庄园 · 地下二层」。每一级可点，点了打开那一级的记录。
3. **附近**：一行紧凑的名字列表，最多 8 个。3D 取同一层的房间（按与当前房间的距离），2D 取同层最近的地标（与世界书方位条目的「邻近」同一算法）。末尾「全部房间」展开整栋楼，只列有房间的楼层。

### 3.2 记录卡的内容

标题；副标题（楼层 · 建筑）；说明；事实列表；出入；包给的其余行（面积等）；图集入口；「编辑」按钮；「世界书档案」（默认收起）。

### 3.3 去掉的东西

- 署名链接：移出地点页。署名已在设置页，包的署名照旧可见（brief §7 对原作者署名的要求不受影响）。
- 空楼层行：没有房间的楼层不画；有房间的楼层也只在「全部房间」展开后出现。
- 「地点」页里单独的建筑简介块：建筑就是一条记录，玩家不在任何房间时它就是第 1 项。

## 4. 世界书档案就是同步出去的那条条目

### 4.1 一个生成器

`map/core/place-record.mjs` 的 `entryText(record)` 是条目正文的唯一来源。生成器 `tools/build_worldbook_addon.py` 用它写条目；查看器的档案显示同一个函数对同一条记录的输出，再与书里实际的正文比对（§4.4）。卡片字段、档案、书里的正文因此不会各说各的。

### 4.2 房间条目：每间一条

| 方案 | 条目数 | 新增字符 | 一次触发的 tokens | 每轮典型（JIT 关） | 每轮典型（JIT 开） |
|---|---|---|---|---|---|
| A 每间房一条，关键词 = 房间名与叫法 | 71 | 约 5100 | 平均 62，最多 98 | 提到 1–3 间：60–190；一段参观提到 10 间：约 620 | 只有当前楼层的房间可能触发：60–190，上限是当前楼层全部（一层 30 间约 1060） |
| B 每层一条，一行一间，关键词 = 该层所有房间名 | 5 | 约 3300 | 一层 1064、二层 832、地下二层 724、三层 417、地下一层 255 | 提到任何一间就整层发出：255–1064；跨层 2 条约 1900 | 同左（JIT 只能整条开关） |

数字的算法：84 个房间节点里有说明或出入的 71 个；正文为「<地点·名>」包裹的一行「名：建筑 楼层。说明。出入：…」；tokens 按生成器的 `tokens()` 粗估（中日韩字符一字一个，其余四字符一个）。现有附加书常驻部分约 3950 字符，关键词条目约 11600 字符。

**选 A。** 理由：典型一轮里 A 比 B 省 5–15 倍；每条正文正好是一间房的记录，档案能一对一显示；用户改一间房只影响那一条。代价是书里的条目从 58 条变成 129 条，常驻部分不变（新条目全是关键词触发）。

细则：

- 条目 id `map.room.<节点 id>`，类别 `places`（`SHIP_CATEGORY_PREFIXES` 加一行），名字「地点-<房间名>」，位置与现有「地点-*」条目相同（关键词触发、角色定义之前、深度 4）。
- 只有说明、事实或出入至少有一项的记录才生成条目。13 个只有名字的房间（走廊、设备间、前廊等）没有条目：一条只写「走廊：地下二层」的条目只会被常见词反复触发，不给模型任何新信息。它们的档案写「这个地点还没有说明，所以世界书里没有单独的条目」，旁边是「编辑」。
- 通用名（在一个包里出现于两栋以上建筑，或在生成器的通用词表里：走廊、设备间、储藏室、客房、连廊等）加次要关键词：所在建筑的名字与叫法，逻辑「任一」。这样别的宅子里提到「储藏室」不会发出这栋楼的条目。发布物的条目形状加 `strategy.keys_secondary { logic: 'and_any', keys }`。
- 常驻条目「地图当前地点」不变：它是叫法词表，正文一字不改。
- 世界地名和地标：已有「地点-*」条目的 42 处照旧；其余地标的说明在三条方位条目（EJS，只展开当前地点那一行）里。档案对这些地标显示方位条目里属于它的那一行，条目名写「地图方位·<层名>」。地标不另建条目。

### 4.3 JIT 开着时

`map/tavern/spatial-contract.mjs` 的 `activationOf` 在玩家位于房间时只返回这间房的名字（`locate` 没有标记 id，就没有邻近）。房间条目上线后，JIT 会把同层其他房间的条目全部停用。PLACE-1a 把激活集扩成：当前房间 + 同一楼层的房间 + 所在建筑名。玩家在城里时，房间条目全部停用，提到也不发。

### 4.4 档案卡显示什么

- 条目名、条目正文（去掉首尾的包裹标签行；「显示原文」可看完整正文）。
- 同步状态，一行：「已同步 · 版本 0.9.7+9c5325f9 · 本机 10-02 14:05」。时间是这台设备上一次自动同步成功的时刻，存在新的本机键 `edenMapWbSyncAt`（在 `map/core/storage.mjs` 登记，不是开关）。
- 三种状态：已同步；「酒馆里改过」（书里正文的指纹与写入时不同，同步保留了用户的改动，上游新文字收起在下面）；「还没同步」（书不存在或版本落后，下面显示待写入的正文）。
- 本聊天有用户改动时，见 §5.4。

### 4.5 查档案的协议

查看器发 `eden-map:th { op: 'wb-peek', id, name }`。宿主先按 `id` 在发布物的 `index`（生成器写的「记录 id → 条目 id 列表」）里找条目 id，再按 `extra.eden_id` 在已装的附加书里取正文；同时在本聊天的自定义书里取这个地点的条目。回 `eden-map:wb-peek { id, name, entries: [{ book, name, content, ver, at, state }] }`。没有 `id` 的包（或发布物没有 `index`）退回今天的名字匹配。消息字段在 `map/core/protocol.mjs` SCHEMA 登记。

## 5. 用户编辑

### 5.1 一个入口、一个编辑器

每张地点卡、房间卡、区域卡和建筑卡上一个「编辑」按钮，打开同一个编辑器。字段：

- 名称（单行，≤ 40 字）
- 用途（单行，≤ 200 字）
- 说明（1–3 句，≤ 400 字）
- 事实（列表，可增删，每条 ≤ 120 字，最多 12 条）
- 叫法（别名，可增删）

每个字段下面浅色显示包里的原文。每个字段有「恢复成包里的」。

人物卡用同一个编辑器：自定义数据本来就有 `character` 类，名称、说明、事实、叫法都适用，「用途」对人物不显示。物品卡不用：物品行有数量、来源、持有人，形状不同；物品卡保留现有的「这不是物品」。

### 5.2 存在哪里

聊天变量 `<聊天变量>.自定义.items[<键>]`，在 `stat_data` 之外（brief 规则 5）。现有字段 `类`、`名`、`用途`、`别名`、`源` 不变，新增（K-R135）：

- `说明`：字符串
- `事实`：字符串数组
- `基于`：保存时包原文的指纹 `{ 字段: hash }`，用来发现包后来改了（§6）
- `楼`：保存时的楼层号，用来与剧情标签排先后

键：有节点的包用节点 id，否则用标准名。旧数据的键是标准名，加载时经节点树换成 id；换不到的照旧按名字认，什么都不丢。

撤销：`自定义.撤销` 保留本聊天最近 20 次改动的前值。编辑器保存后的提示条带「撤销」，编辑器里也有。

可重算：记录 = 包数据 ⊕ 从聊天楼层重放的 `⌖改名 / ⌖用途 / ⌖事实` ⊕ 手动改动。手动改动是用户在这个聊天里的明确操作，和今天的自定义块一样随聊天变量走；缓存丢了重算结果不变。同一字段上，剧情标签和手动改动按楼层先后，后来的为准。

### 5.3 自动同步到本聊天的自定义书

本聊天的书「<包名>·自定义·<聊天短哈希>」（只动带我们标记的书和条目）改成两类条目：

- 一条常驻索引：只有名字对照（「书房→星图室」），与今天 `summarizeCustom` 同一格式，≤ 220 字。
- 每个有说明、用途或事实的地点一条关键词条目：关键词 = 标准名、用户起的名字和叫法；正文由同一个 `entryText` 生成，开头一句「本聊天里以此为准」；插入顺序排在附加书的同名条目之后。

保存即同步，沿用 `root-store.mjs` 的 `customChanged → syncWb`。「同步到世界书」开关保留在设置里，含义不变。

### 5.4 包原文怎么处理

用户改动只覆盖，不删除。附加书是全部聊天共用的一本，里面这个地点的条目原样留着；本聊天的自定义条目排在它后面，并写明以本聊天为准。档案卡显示合并结果：上面是「本聊天的改动」（自定义书里的条目），下面收起的是「包里的原文」（附加书里的条目）。「恢复成包里的」删掉本聊天的改动和对应的自定义条目，附加书不动。

## 6. 修订

- **包或生成器改了一个地点**：重跑 `tools/build_worldbook_addon.py --ship`，发布物的 `ver` 变化；下次打开地图时自动同步合并（`worldbook-sync.mjs` 现有流程）；档案显示新正文和新版本。
- **用户在酒馆里手改了附加书条目**：现有的合并保留用户正文并记 `eden_conflict`；档案标「酒馆里改过」，上游新正文收起显示。
- **用户在本聊天改过，包后来也改了**：用户改动仍然为准。保存时记下的 `基于` 指纹与现在的包原文不同，编辑器和档案卡上标「包里的原文有更新」，两段都显示，包原文默认收起。
- **门禁**：生成器测试锁住「每条有文字的记录恰好有一条条目，条目正文 = `entryText(记录)`」；`check_maps.py` 继续保证 `addon_places.json` 与地图数据同步。

任何一种情况下都没有文字被悄悄丢掉。

## 7. 要不要重做自定义

**建议：要合并，存储不推倒。** 一个地点一条记录，一个编辑器，每张卡一个「编辑」按钮。不为每个功能单做界面。存储继续用 `<聊天变量>.自定义`，加几个字段；剧情标签照旧。

### 7.1 今天的入口

1. 设置 → 自定义 → 名称与用途（`map/custom-names-view.mjs`）：聊天变量，名称 / 用途 / 叫法，同步到本聊天的自定义书。
2. 房间卡底部的「自定义名称 / 自定义简介」输入框（`map/ui/room-gallery-panel.js`）：存在本机 `edenRoomCustomV1`，全部聊天共用，不进聊天变量，不进世界书。
3. 剧情标签 `⌖改名 / ⌖用途`：写进 1。
4. 剧情标签 `⌖事实`：开了 C8 才写进附加书。
5. 「未上图」指派：给标准名加叫法，写进 1。
6. 编辑模式（K-R100）：包作者改位置、父节点、叫法、图片，存在本机的包草稿，不进聊天。

### 7.2 去掉的
