## 2. 五大浪费的五问

**W1 中低层 8K 整张重渲 5 次（约 3–4 GPU·h + 返修时间，估）**
1. 为什么重渲？每轮评审都在全图上提出接缝、灯光、屋顶这类问题。
2. 为什么全图？当时没有局部重渲 + 合成的工具。
3. 为什么没有？render-performance.md 的“还能做的”第 4 条早就写了“只渲变化的区域”，但一直没排进计划。
4. 为什么没排？任务按“出下一张图”推进，没有人负责工具投入。
5. 根因：**没有“同一资产第 2 次整张重渲前必须先做局部补丁工具”的规则**。最便宜的拦截点是 A3 第二次 8K 之前。

**W2 伊甸 three.js 线整体作废（约 8–12 agent·h，估）**
1. 为什么作废？门控 6.5 分不过，用户手机上看是像素化的。
2. 为什么前面评审给了 9 / 8 / 8.5？评审人设（architect / interior / luxury_marketer / interaction_perf）都在桌面截图上打分，**没有手机人设**。
3. 为什么一开始选 three.js？沿用了既有代码，没有先做写实路线的风格帧对比（用户记忆写明“不要平面矢量风，Blender 写实打底”）。
4. 根因：**技术路线没经用户看风格帧就开工；评审看不到用户实际使用的环境**。最便宜的拦截点是 b37c6ec 之前，先交一张风格帧 + 一张手机截图给用户。

**W3 上层重新合成（v7）与岛影往返（约 1 GPU·h + 3 agent·h，估）**
1. 为什么重渲？estate2 的伊甸比上层底图晚定稿，尺寸和停靠平台都变了（锚点 0.6024 → 0.5939，见 00:01 提交）。
2. 为什么先渲底图？任务是并行派出去的，没有依赖图。
3. 岛影为什么做了又删？用户没批准就当成默认效果加上了（bbe0d92）。
4. 根因：**没有资产依赖顺序；新视觉效果在用户点头前就进了默认值**。最便宜的拦截点是并行派发之前画一张依赖表。

**W4 自编名字**
1. 为什么改名？地点名是按意思转写的，或者起了占位名，后来又加了一层运行时绑定（01:44）。
2. 结果：10f6c2c 按用户意见删掉绑定层、改回原名。这次改动还误回退了圣铁摇篮的提交，之后才恢复。
3. 根因：**没有“名字必须带卡内行号”的校验**。最便宜的拦截点是 check_maps 里做名字对账。

**W5 非卡内容**（顶楼、别墅 10 栋、飞艇、小教堂、售货亭）
1. 为什么出现？建模 agent 为了让画面“丰富”自行补内容。
2. 为什么没拦住？评审看的是“好不好看、像不像”，fidelity 人设只在 card 组里有，art / estate 组没有。
3. 根因：**art / estate 评审组缺少卡对齐人设**。最便宜的拦截点是草稿阶段的清单比对。

## 4. 反馈回路延迟

- **路径**：渲染 → 切 DZI → 提交 → 推送 → jsDelivr 缓存 → 用户在酒馆里开跟随分支预览。
- **卡住**：跟随分支预览在“没梯子”的网络下会停在旧提交上，由 0b31d3d（head.json 头指针）和 e867fa8（第二节点、按分钟破坏缓存）修复。grep：jsDelivr=65、purge=29、卡在旧=5。
- **延迟**：从推送到用户看到新图，典型 10 分钟到数小时（**估**；会话中“10 分钟检查一次”出现 108 次，说明普遍在轮询等待）。
- **后果**：庄园手机问题是用户实测后才暴露的（10:23 NOTES）。如果每轮都有手机截图直接给用户看，W2 可以提前约半天发现（**估**）。
- **改进**：每轮草稿在聊天里直接附 375 px 截图，不依赖 CDN；预览只用于最终确认。

## 5. 编排与成本

- **GPU 争用**：本机只有一块 Metal GPU，但常有 2–3 个 agent 同时想渲染。124 个任务输出里出现 Blender（**实测**，grep -l），52 个出现 crash，38 个出现 pkill（**实测**）。全局 `pkill blender` 会误杀别的 agent 的渲染（**估**，任务输出里未逐条核实）。**规则**：只允许按自己的 PID 杀进程；GPU 用锁文件（`/tmp/eden_gpu.lock`）排队。
- **Metal 崩溃**：kernel 缓存编译时 `NSURL fileURLWithPath` 抛异常，与中文路径“性能/”有关（grep:kernel=3）。**规则**：统一用 ASCII 的 TMPDIR 和工作树路径。
- **工作树 / 推送冲突**：
  - 10f6c2c 误回退他人提交；
  - 浏览器测试端口冲突，已改为按路径哈希到 5200–5999（09-27 23:44 提交）；
  - heredoc 写出 0 字节文件（grep:heredoc=24），smoke 后来加了空文件检查（09-28 00:05 提交）；
  - 中文路径的 pathname 编码问题（00:19 提交）。
  - **根因**：多个 agent 共用一个分支，但缺少“rebase + bump_head”的统一入口。现在已由 bump_head.py 解决。
- **模型与额度**：会话中 Opus 出现 254 次、Sonnet 57 次，派出子 agent 54 次（**实测**，grep）；rate limit / usage limit 共 8 次（**实测**）。模板化工作（第 N 个地标、文档同步、瓦片重切）占了大头，却都用了 Opus。用户记忆规定“只用 Opus”，所以现阶段的省额度手段只能是：**少派 agent、少开评审轮次、让评审人设读缩略图而不是 8K**。如果用户放宽规定，建议地标批量、切片、文档同步用 Sonnet，设计决策与评审仍用 Opus。

## 6. 质量上限

- **手机清晰度**：底图 8K 覆盖整个天城。小岛（直径约 200 m）在 8K 上只有约 100–200 px（**估**，按 0.375 m/px 的上层比例）。放大到最后一级 DZI 也只能看到色块。**对策**：每个重点岛单独渲 2–4K 高清裁片，作为 DZI 的叠加层（OpenSeadragon 多图层），而不是把整张底图升到 16K（渲染时间约 4 倍，**估**）。
- **glb 预算**：标准档约 2.8–4.8 MB（**实测**：041724e、6427b34）。手机上首次加载在弱网下需要数秒。**对策**：
  - 贴图预算：每栋 ≤2 张 1K webp 图集；
  - LOD：外观用低档，点进室内再加载标准档；
  - 烘焙：AO + 光照烘进顶点色或贴图，减少运行时灯光。烘焙前要自动查纯黑，湖岸黑块就是烘焙失败漏出来的。
- **写实路线的边界**：Cycles 俯视在 375 px 屏上细节会糊成一片。可读性靠的是**色块分区 + 标签**，而不是更多几何。地标批量做得好，是因为**单栋、明确参考、共享材料、固定相机**。把这套模式推广到庄园和底图，比继续加细节更能提高质量。
