## 〇、方向结论：没有反，但顺序要调

- **不推倒重写**：现有脚本有 600 多条测试，积累了大量酒馆宿主的坑位处理（MVU 生命周期、CDN 线路、流式性能、休眠唤醒……），重写会把这些全丢掉。
- **也不能继续「从伊甸往外抠」**：v4 的 schema 本质上是「把伊甸的形状推广开」。`guess_order`、`up_alias`、`outside`、`zones` 这类字段都是给伊甸打的补丁，越抠越乱——这正是你「感觉 schema 还要优化」的原因。
- **正确的做法：契约先行 + 渐进迁移**（绞杀者模式）。
  1. 先定一个**最小内核契约**：只有一棵「节点树」是必需的，其余全部是可选能力模块。
  2. 用一个「最小包」（几个节点、没有底图）当试金石，**现有引擎必须能在它上面跑起来**。
  3. 引擎内部通过兼容读取器，把伊甸现有的数据文件（`maps.json` 等）换算成新契约，伊甸数据**不用一次性重写**。
  4. 然后一个模块一个模块地让引擎只认新契约，每一步脚本都照常能用。
- **「最小系统」不是另起炉灶**：它的含义是「现有引擎在最小包下也能用」。这个能力本身就是给别的卡的保底（原 S8）。

## 一、总览：什么定死了，哪些该改成可自定义

原则：**内核定死「形状」**（协议、实体基本字段、渲染积木、安全规则）；**作者改「内容」**（节点、名字、分类、字段、样式、规则文本）。

| 领域 | 现在定死在代码里的 | 应改为作者可自定义 | 应保持内核定死 |
|---|---|---|---|
| 空间 | ① 地图种类 `world/points/estate`，其中世界图和剖面只有伊甸能用；<br>② 当前地点匹配写死 6 级（庄园房间 → 区域 → 地标 → 层 → 天城 → 世界）；<br>③ 事件另有一套独立地理（`LAYERS`/`RE_*`/`ZONES`）；<br>④ 室外区域、房间没有 parent | 节点树：任意深度，节点类型的名称由作者自己起，别名、弱关键词、坐标都挂在节点上；视图（底图瓦片 / 示意图 / 三维）挂在节点上 | 匹配算法（最长别名、偏向更深的节点）；节点 id 规则 |
| 时间 | 默认 MVU 路径（`世界.当前时刻`…）；时段固定 4 档 | 时间来源路径；时段的名字和分界点 | 确定性时钟推进规则（零 Token） |
| 人物 | 名册「三张表」的结构；固定字段槽位（等级 / 核心值 / 代号 / 外界知情 / 饰物 / 战力…）；阶段梯度、战力梯度、头像白名单、分组名 | 名册分组（名称 + 数据来源）；属性字段列表（字段、标签、显示方式：文本 / 计量条 / 梯度 / 小签）；头像来源 | 实体核心字段 `id/name/node/source`；多来源的优先级仲裁 |
| 物品 | 拾取动词表写在 core；两处存储；三套 id | 拾取词表和黑名单（按语言、按包）；世界藏物数据 | 统一的 stash 结构；账本对账规则；「聊天记录是唯一真相」 |
| 事件 | 伊甸分类写在代码里；寿命 / 合并窗口 / 每楼上限都是常量；特效和图标写死 | 分类（是什么）、图标、颜色、特效（用积木加参数组合）、寿命、注入句模板 | 标签语法 `⌖类别｜地点｜等级｜一句话｜发布方`（与模型的协议）；内容一律不过滤 |
| 图层 | 固定的 9 个模块，包只能喂数据 | 声明式图层：类型 + 数据来源 + 适用层级 + 样式 + 菜单 | 10 个槽位的顺序；渲染积木（点 / 区域 / 线 / 标签 / 着色 / 粒子 / 沿线移动） |
| 界面 | 抽屉页签；按地图写死的主题；图例；产品名；约 30 条带卡口径的文案 | 文案（`strings`，已有）、主题令牌、图例、署名、启用哪些页签 | 设计令牌体系；z 阶梯；无障碍基线 |
| 与模型的接口 | 注入句格式（中文写死）；世界书构建器是伊甸专用 Python；`[TOPO]` 前缀 | 注入模板、世界书规则条目（非伊甸包已支持） | 注入预算与降级顺序；只写我们自己的附加书；同意开关 |
| 宿主 / 平台 | —— | ——（只有 MVU 路径可配） | MVU / 酒馆助手适配、存储命名空间、CDN 线路、消息协议 |
| 三维 | 伊甸庄园页（`map/estate/main.js`）是专用代码 | 三维清单（已支持）、热点、区域 → 子图锚点 | 通用三维查看器 `viewer3d.html` |

## 二、内核契约 v2 草案（S1 的产出，要你过目）

```
manifest.json      必填只有 id / schema:2 / title；可选 lang（zh/en…，决定默认词表和注入模板的语言）、match（按卡自动选包）
                   包从哪来（S9）：卡内嵌 → index 匹配 → 用户填的网址或本机文件 → 0 档自动
├─ nodes     节点树 = 唯一地理（可选：不写就由聊天自动生成 → 零配置保底）
│    { id, name, alias[], hints[], parent, type, at?, view?, canon: card|inferred }
│    hints = 弱关键词：只用来判断「属于哪个祖先」，不直接落点（取代伊甸的 RE_UP/LOW/MID 正则）
├─ views     怎么画：tiles（DZI 底图）| schematic（自动示意图）| model3d（三维清单）；挂在节点上
├─ vars      MVU 路径：地点 / 时间 / 时段 / 日期 / 着装 / 名册表
├─ entities  名册分组 [{id,label,source}] + 属性字段 [{field,label,kind,ladder?,max?}] + 头像来源
├─ items     世界藏物数据 + 拾取词表 / 黑名单
├─ events    分类（只管「是什么」）：groups / types{icon,color,fx,life,inject} / fx_presets / levels
│            「在哪」统一交给节点别名，不再有 layers / match / guess_order / outside / zones
├─ layers    声明式图层 [{id,type,source,slot,applies,style,menu,legend}]
├─ ui        strings / theme / legend / credits / tabs
└─ llm       注入模板 / 世界书规则条目
```

- **兼容**：新增 `core/compat-v1.mjs`，把 v1（`maps.json` + `events.json` + 旧 manifest）在内存里换算成 v2。伊甸和 town 两个现有包不用改文件就能跑。schema v1 冻结不变；新包直接按 v2 写。
- **自动降级**：没写 `views` → 示意图；没写 `events` → 通用中性分类；没写 `vars` → 按字段名自动发现；没写 `entities` → 只显示名字和位置；没写 `layers` → 用内置默认层。
- **最小包** `map/packs/minimal/`：只有 5 个节点，没有底图。引擎的当前地点、事件、人物、物品必须全都能跑，由测试钉死。

1. 导入统一脚本；

## 十一、给 Sonnet 的提示词：固定骨架 + 按步骤调整详细程度

- **骨架固定**：每份提示词都用同一套小节，方便你审核，也方便我审 Sonnet 交回来的结果。
- **详细程度按步骤调整**：
  - 设计类步骤（S1、S3、S8、S9）写到接近规格书的程度，约 150–300 行；
  - 搬运类步骤（S4 文案、S5 改名）给出对照表；
  - 小修只写几十行。
- **「细」要细在精确，不是写得长**：写清确切的文件和行号、改前改后、验收断言、什么情况下停手。长篇解释和重复规则反而会稀释重点、制造前后矛盾。
- **通用规矩不在提示词里重复**：Sonnet 在仓库里跑时会自动读 CLAUDE.md，S0 之后再加上 `docs/ARCHITECTURE.md` 和 `docs/naming.md`。提示词里只写「本步特有」的内容，外加「先读这几份」的指针。
- **一份提示词对应一次推送的量**（2–3 项）。结尾必须停下来汇报，不许自动接着做下一步。
- **汇报语言**：Sonnet 按 CLAUDE.md 用英文写短报告；你贴回来后，我给你中文解读和下一份提示词。

提示词骨架（英文发给 Sonnet；每份附一段中文说明给你看）：

```
# Task <S-id>: <one-line goal>
## 0. Why (2–4 lines of context; link the plan section)
## 1. Read first (exact files + line ranges; docs/ARCHITECTURE.md, docs/naming.md once they exist)
## 2. Scope — IN (numbered) / OUT (explicit non-goals: do not touch …)
## 3. Setup (worktree command; baseline: node --test + smoke must be green before any edit)
## 4. Tasks (numbered; per task: files, exact change, before→after, functions to reuse)
## 5. Constraints (task-specific red lines on top of CLAUDE.md)
## 6. Tests to add (file names + the assertions they must make)
## 7. Verify (exact commands + expected result)
## 8. Commits & push (commit boundaries + English messages; push command; CI check)
## 9. Stop and report instead of guessing when … (parity mismatch, schema ambiguity, push rejected, test count drops)
## 10. Report format (≤10 lines English: done / tests / open questions / file paths; cleanup confirmed)
```

## 十四、工作量口径 + 模型与推理档位 + GitHub 瘦身（v9 新增）

### 14.1 工作量不按小时估，按「规模档 + 提示词份数」估

按小时估不准：同样一件事，模型快慢、要返工几轮，差别都很大。改用下面两个能数得出来的量：

| 档 | 判定 | 一份提示词能否做完 |
|---|---|---|
| **S** | ≤5 个文件、≤200 行改动、只跑单测 | 1 份 |
| **M** | 5–15 个文件、≤600 行，要加 1–2 个探针 | 1 份 |
| **L** | 15 个以上文件，或者改到跨模块的契约 / 数据，要对拍测试 | 拆成 2–3 份 |
| **XL** | 新契约 / 新 schema / 架构取舍，需要判断力 | 先由 Opus 出设计（1 个会话），再按 L/M 拆给 Sonnet 实现 |

**全计划估算（A–D 阶段）**：Sonnet 提示词约 **32 份**，Opus 设计 / 审核会话约 **7 个**，外加 2 轮真实酒馆测试。进度按「完成了几份提示词」来算。

### 14.2 推理档位：按任务分类，不统一

依据官方页面（anthropic.com/claude-sonnet-5-5，2026-09-30 查阅）：

- 档位有 Low / Medium / High / Xhigh / Max 五档。Claude Code 默认是 Medium。
- 官方对档位的说法：低档「更快、更省 token，适合常规工作」；高档「推理更久，并且更彻底地检查自己的工作」。
- 官方对两个模型的分工：Sonnet 5.5「最擅长范围明确的日常任务、修 bug」；Opus 5.5「在需要持续判断的复杂开放任务上明显更强」；Sonnet「以较低档位与 Opus 搭配时互补效果最好」。

据此分四类：

| 类别 | 例子 | 模型 · 档位 |
|---|---|---|
