# 每轮新增一位「现编」审阅者（元提示词，给编排代理看）

**规则（用户 2026-09-27）**：固定人设会漏掉新问题。每一轮审阅，除了 `personas/` 里的固定人设，**必须**再加一位根据本轮情况现编的审阅者。所有审阅者都用 Opus。

## 编排代理怎么做
1. 先读这些材料（`pack.py` 生成的 `brief.md` 已经摘好了大部分）：
   - 本轮 diff：`git diff --stat <上轮提交>..HEAD` 与关键文件的实际改动（脚本、查看器、数据）。
   - `NOTES_FROM_LOCAL.md` 最后两三节（云端 / 本机刚说了什么、留了什么坑）。
   - `docs/GOAL_v0.9.1.md` 最近改动的行、带「用户 2026-…」的原话（用户最新的要求）。
   - 上一轮的审阅报告和架构师裁决（`docs/reviews/<门控>/`），特别是「遗留」和被判「不采纳」的意见。
2. 找出**固定人设覆盖不到**的风险：本轮新加的东西（新图层、新交互、新数据格式、新素材来源）、用户新提的要求、上一轮的「遗留」、改动顺带可能弄坏的旁边的东西（回归）。
3. 据此现编一位审阅者，写清：
   - **身份**：一个具体的人（职业 / 使用场景 / 设备 / 关心什么），不是「综合审阅」。
   - **为什么选他**：一两句，指向本轮具体的改动或用户原话（引用 diff 里的文件名或 NOTES / GOAL 的句子）。
   - **只看什么**：3–5 个检查点，必须落在本轮改动上；每个检查点写清证据要求（截图、数字、坐标、复现步骤）。
   - **不看什么**：固定人设已经覆盖的方面，避免重复打分。
   - 输出格式与门槛：同固定人设（分数 X/10、最多 5 条问题带级别和修法、一句话结论）。
4. **每轮必须不同**：不能和前几轮的现编人设重复（身份或检查点重复一半以上就换）。把本轮的现编人设连同「为什么选他」写进 `docs/reviews/<门控>/fresh_r<N>.md` 开头，下一轮编排时先读历史，避开。
5. 他的分数与固定人设同等计入门控：低于门槛或有 P0，门控不过。架构师汇总时单列一行「现编：<身份>」。

## 例子（只说明格式，不要照抄）
- 本轮 diff 主要是 `blender/tc_city.py` 的交界起伏线 + NOTES 说「云端把岛轮廓改成多边形」→ 现编「用地图找路的出租车司机（夜班）」：只看交界大道能不能连续开过去、路口是否被楼压住、岛影下的路是否还读得出；证据：8K 局部里标出三条贯穿交界的路线。
- 本轮 diff 是 `map/viewer.html` 的层按钮改到底部 + 用户说「以后会在伊甸上加建」→ 现编「左手持机、屏幕开了大字体的中年玩家」：只看底部按钮与系统手势区、放大字体后按钮换行、加建后楼层条会不会溢出；证据：375 × 812、系统字体 130% 的截图。

## 模板（填好后作为该审阅者的提示词）
```
你是「<身份>」。之所以请你：<为什么选他，引用本轮改动 / 用户原话>。
先读简报 {{BRIEF}}。只看以下几点（其余方面已有其他审阅者）：
1. <检查点>（证据：…）
2. …
不改任何文件，不做 git 操作。独立打分，只看现在的绝对水平。这是第 {{ROUND}} 轮。
输出（中文，简短，写到 {{OUT}}）：分数 X/10；最多 5 条问题（级别 P0/P1/P2、位置、现象、修法）；一句话结论。
```
