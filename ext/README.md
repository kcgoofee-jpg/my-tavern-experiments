# Eden Map extension loader (F2)

> Status: v0 loader, lands with the S10 repo split. Chinese edition: `README.zh.md`.
> Evidence base: `docs/extension-study.md` (measurements, TH dependency map, recommendation A→F line) and
> `docs/delivery.md` (DIST-3 gh delivery lines). Real-tavern steps are a user checklist, never automated here.

## What this directory is

The whole `ext/` directory is the future extension repository (S10 split). After the split it becomes the repo
root: SillyTavern / TauriTavern install an extension by `git clone`-ing a repo whose root carries
`manifest.json`. The main repo (~944 MB, art included) can never be installed as an extension — that is why the
loader is separate. At the split: copy `ext/*` into a new repo root (one commit of history is enough; see
`docs/plans/spatial-os.md` S10b) and register the new repo address in `docs/delivery.md` §3.

Files:

| File | Role |
|---|---|
| `manifest.json` | ST/TT extension manifest (CCST field shape): `js: index.js`, `css: style.css`, `auto_update: true` (safe only because the loader holds no state — see §TT specifics; after any update TT still needs a full quit + reopen) |
| `index.js` | loader: version pin, integrity check, native adapter swap, engine import, per-card enable, settings drawer, handshake |
| `loader-core.mjs` | pure helpers (line table, URL build, head check, card allowlist, integrity verdict) — unit-tested in `tests/f2_ext_loader.test.mjs` |
| `style.css` | drawer rows and the failure notice only; everything else keeps the engine's own styles |

## How it loads the engine

1. `head.json` is fetched from the branch on all three gh lines (cache-busted), the largest `build` wins
   (same rule as the follow loader). The engine is then pinned to that commit sha.
2. `map/data/integrity.json` (generated by `tools/build_integrity.py`, regenerated by `tools/bump_head.py`
   with every head bump) is fetched from the branch; its `head_sha` must match the head we just picked.
3. **Every code file in the manifest is fetched and SHA-256-checked before anything is imported.**
   Any mismatch or unreadable file → fail closed: nothing is imported, one plain notice is shown.
   (Idea borrowed from `ykny12058/ilw-native-owner` — the idea only, no code, no licence entanglement.)
4. `map/tavern/host-adapter.mjs` + `map/tavern/host-native.mjs` are imported from the same line and sha, and
   F1's native adapter replaces the groups of the `hostAdapter` singleton — every engine call then goes
   through native ST APIs (`getContext()`), business modules untouched.
5. `map/tavern/eden-map.js` (the same entry the TavernHelper script imports) is imported. The viewer, packs
   and art keep loading from CDN exactly as in script form.

Lines (`loader-core.mjs`, per `docs/delivery.md` §3): `cdn.jsdmirror.com/gh` → `cdn.jsdelivr.net/gh` →
`fastly.jsdelivr.net/gh`; each `fetch` races a 10 s timeout and falls through to the next line.
`cdn.statically.io` and `raw.githubusercontent.com` stay excluded (F-TT / DIST-3 measurements).

## Double-load handshake

- The extension sets `__edenMapExtInstalled` on the page at boot. The script-form entry
  (`map/tavern/eden-map.js`) sees it and mounts nothing — the two forms never run side by side on one page.
- Conversely the loader checks `__edenMapIds` (the script's instance registry) before mounting: if a script
  instance is already alive on the page, the extension yields and says so.
- Switching forms takes a full restart (TT does not reload extension JS on `/reload-page`).

## Only on chosen cards

The drawer has 「只在选定的卡上启用」 (default off = every card, same as today's global script). When on, only
cards whose name or index is in the list get the map; other cards show nothing (the script form yields while
the extension is installed, so an unlisted card has no map in either form — that is what "only these cards"
means). Settings live in `extension_settings.eden_map_ext`, which survives a wiped clone dir (measured,
`docs/extension-study.md` §3.5).

## TT specifics (F3)

- **An update wipes the clone directory** (everything except `.git`, measured `docs/extension-study.md` §3.5), so
  nothing under `ext/` may keep state: the loader and `map/tavern/host-native.mjs` touch no localStorage /
  sessionStorage / IndexedDB / cookies (pinned by `tests/f3_ext_state.test.mjs`). Settings live in
  `extension_settings.eden_map_ext`, map state in chat variables and the webview's own storage — all outside
  the clone dir, all survive a wipe. **After any update (auto or manual): fully quit and reopen TT** —
  `/reload-page` does not reload extension JS.
- **Clipboard and save in WKWebView**: the web clipboard can hang forever instead of rejecting, and
  `<a download>` is ignored outright (CCST real-machine findings, `docs/extension-study.md` §7).
  `map/app/transfer.mjs` runs the proven three-tier chain — TT's own bridge
  (`__TAURI__.core.invoke('plugin:clipboard-manager|write_text')`, found along the window→parent chain),
  then the web clipboard behind an 800 ms timeout, then a hidden textarea + `execCommand('copy')` (WebKit
  needs ≥2 px and no `setSelectionRange`, verified in `tools/browser/f3_tt_webkit.mjs`). Saving a file in TT
  becomes copying; when every copy path fails, a manual-copy panel opens with the text preselected. External
  links go through `plugin:opener|open_url` where present.
- **Chat surface**: the leak fence reads rendered floors through `hostAdapter.ui.displayedMessage` — in the
  extension form that queries `#chat .mes[mesid]` directly (study §4), so leaked
  `<StatusPlaceHolderImpl/>` / statusbar markup is swept without TavernHelper.

## Mainland install: clone address and zip fallback

- Extension install is `git clone <repo-url>`; GitHub clones from the mainland are unreliable
  (`docs/extension-study.md` §6). A mirror repo address is **not yet tested** (Q-32c open): push a mirror of
  the extension repo (for example a Gitee repo kept in sync, or the user's preferred proxy) and use its URL in
  the install dialog.
- Zip fallback, no git needed: download the repo zip (`.../archive/refs/heads/main.zip` via any reachable
  mirror), unzip, and drop the folder contents into `data/extensions/third-party/eden-map-ext/`
  (`manifest.json` at that folder's root). Restart the tavern fully afterwards.
- The runtime engine still comes from the three gh CDN lines, so the clone problem only affects installing
  the ~30 KB loader, not the map itself.

## Optional route, recorded but NOT shipped

An extension may carry its own MVU build so a plain card could run the map without TavernHelper
(measured possible, `docs/extension-study.md` §3.3 「没有 TH」 row). Decision for now: do not fork MVU. The
Eden card's `stat_data` is written by the card's own MVU scripts, so the Eden card needs TH either way;
a forked MVU would drift. Revisit only if a non-TH pack is requested.
